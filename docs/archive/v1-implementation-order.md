# v1 implementation order

> Finished history, kept as written then: its dates and its "now" are of that time. What is true now is in [design/](../design/).


Decided 2026-10-27; the tank step and restart recovery were added on 2026-10-28, and the Matrix and restart recovery steps were removed on 2026-10-29, with the numbering unchanged. Each step is a series of small commits; the first five steps do not touch tank. Values not yet decided use the values proposed in this document, and are tuned when the step that needs them is reached.

1. **Skeleton** (completed 2026-10-28): the workspace, a version-pinned `rust-toolchain.toml`, crane plus devenv (with Postgres), and the checks (fmt, clippy, nextest, `max-core`'s dependency allowlist). All checks are the flake's `checks`, and CI runs only `nix flake check --impure`.
2. **`max-core`** (completed 2026-10-28): message types, rendering, the segmenter, the two state machines (the core and intent), and projection, all tested with fakes. The signatures of the two state machines were settled in this step, and the changes made while writing them have been carried into the sections [The core](../design/core.md) and [Intent](../design/intent.md).
3. **`max-db`** (completed 2026-10-28): four migrations covering the platform, ledger, turn, usage and summary parts of the v1 tables (media and memory are added along with their features), plus the queries that the conversation actor and the senders need, all tested with `#[sqlx::test]` (on 2026-10-29 a 6th migration was added, removing the tables and columns used for recovery). The details settled while writing it have been added to [Schema](../design/ledger.md#schema).
4. **`qqbot`** (changed from `onebot` on 2026-10-28, completed 2026-10-29): tokens, the gateway, event and REST types, sending and retracting, with fake openids in the fixtures. The gateway session is a state machine that performs no I/O, and disconnection, Resume, dead connections and each close code are tested within it; the driver is tested against a local WebSocket server. The `listen` example only connects to the gateway and prints events; it sends no messages.
5. **`max-llm`** (completed 2026-10-29): request downgrading and stream parsing for both protocols, Responses and Chat; the parsers perform no I/O. The client sends each request only once and classifies errors with `Error::retryable`; whether to retry is decided by `max`'s model call task, because only that task knows whether any text has already been sent out. Real responses from four providers were recorded for replay tests: cliproxy's gpt-5.6-luna over Responses, with encrypted reasoning passed back verbatim; and cliproxy's Gemini and DeepSeek and the Qwen on taipan over Chat, with `reasoning_content`. Recording revealed two things. First, Responses makes function tools strict by default, which turns every optional parameter into a required one, so `strict: false` is sent explicitly. Second, Gemini reports reasoning tokens without returning any reasoning content; these tokens are not counted in any entry, because an entry's tokens are what it costs the next time it is sent. NInfer's cache breakpoints are an option of Chat: a breakpoint is placed on each user entry that is immediately followed by another user entry, that is, on the blocks of the base context that precede the volatile block; this has been verified on taipan. Images in tool results were downgraded into real images on 2026-10-29 along with `max.image()`; see [Multimodal results](../design/tools.md#multimodal-results).
6. **`maxx` on tank** (completed 2026-10-29): `nixosModules.maxx` generates, by name, the user, the Postgres role and database, the directories, slice, target and service, and runs `max check-config` on the configuration file at build time; `nixosModules.max` is the same module with the post-go-live name. `max` currently does only three things: it migrates the database, asks once who it is using the QQ credentials, and waits for SIGTERM. The QQ AppID and secret are under `maxx/` in sops. The module has a VM test that uses the same Postgres 16 as tank. Deployment ran into two problems. First, sqlx 0.9 does not accept `postgresql://max@/max?host=…` (with a user name, the host cannot be empty), so it was changed to `postgresql:///max?host=/run/postgresql&user=max`. Second, tank's cluster was created on glibc 2.40 while the system is now on 2.42, so the collation version of `template1` did not match and creating a database failed; the version record of `template1` was therefore refreshed (it contains no user objects). The same day, at the owner's request, the records of the `postgres`, `luckperms`, `minecraft` and `matrix-synapse` databases were also refreshed, after `REINDEX DATABASE CONCURRENTLY` plus `REINDEX SYSTEM`.
7. **`max`** (completed 2026-10-29, tested live in the test group): configuration, the conversation table and the conversation actor, I/O tasks, platform senders and `deliveries`, the QQ adapter and `/bind`, commands, and intent. Once it was done came the first run on the real platform: plain-text conversation in the test group, which was also used to test live the items marked for live testing in [The official QQ bot](../design/qq.md). Until step 9, every tool returned the error "工具还没接上，现在用不了。" ("Tools are not connected yet and cannot be used now."). Results of the live test: `/bind` connected the test group; @ conversations and casual chat through intent classification both worked; with the service stopped for 2 minutes and for 10 minutes, the gateway Resumed both times, and @ messages sent during the downtime were redelivered and answered. In the 10-minute case the answer was rejected by QQ (40034005), so the passive reply window is now computed from the message's send time. The same day, at the owner's request, a round of cuts was made: the core gives up when it hits a limit, with no handover (see step 4 of [Processing flow](../design/actor.md#processing-flow)); on restart, turns are interrupted after a grace period instead of being suspended and resumed (see [Restarts](../design/actor.md#restarts)); intent keeps only debouncing, small-model classification and the hourly cap (see [Intent](../design/intent.md)); Max does not send emoticons; and Matrix is deferred. Settled in this step: command output stays in the same conversation (see [Outbound](../design/ledger.md#outbound)); command permissions (see [Permissions](../design/identity.md#permissions)); actor tests use real time (see [Testing the core and the actor](../design/actor.md#testing)); and a stretch of old records attaches to only one group (see [The official QQ bot](../design/qq.md)). The main model on tank is Gemini 3.8 Flash via cliproxy (Chat protocol), and intent uses qwen3.5-4b on h610.
8. ~~**Matrix**, with encrypted rooms and `matrix-bootstrap`~~: removed 2026-10-29 and deferred; see [Matrix](../decisions/matrix-deferred.md).
9. **VMs, MCP, the codemode runner**. The items in [VM processes](../design/vm.md) that first had to be verified on tank were verified on 2026-10-29. The first part was done the same day: the VM service, the `shell` tool, tap, nft and hardening in the module, `max vm-check` and the nested NixOS test, which passed on tank. Addresses are now passed on the kernel command line instead of through DHCP. After deployment to tank it was tested live in the test group: the model called `shell`, the group's VM was up in a little over 3 seconds, and the result came back to the model. The first attempt made no call, because the system prompt still contained step 7's sentence "工具还没接上，别调用" ("tools are not connected yet; do not call them"). The same day, at the owner's request, the prompt began calling it maxx (previously Max). The Haskell version on tank was removed the same day, with its data kept for the import. The second part was also done the same day: the MCP service, the runner in the guest, `run_code` and the first tool to be opened up, `context_read`; the approach is described in [The guest's calls](../design/tools.md#the-guests-calls). The runner's tests run locally with Node against the real MCP service; in the nested test, `vm-check` runs a program that queries the database through the MCP service.
10. **historian** (done 2026-10-29, removed 2026-10-30, changed back to a per-group switch that evening, removed again 2026-11-02; see [Summaries](../decisions/no-summaries.md)): capture, `summary_runs` and `/compact`; moved onto the generic driver that day, then split back out to do its own scheduling.
11. ~~**Restart recovery**~~: removed 2026-10-29; on restart, turns are interrupted after a grace period; see [Restarts](../design/actor.md#restarts).
12. **Media** (started 2026-10-29): the first piece after v1, in six small steps (sending images and the sticker library were added on 2026-10-29); see [Media](../design/media.md). Small step 1 was done the same day and deployed to tank: an image in the test group was downloaded within half a second of being entered in the ledger. Small step 2 was done the same day: media handles, images in entries, downgrading for both protocols, and attached images; the owner decided not to support models that cannot view images.
13. **Web search** (done 2026-10-29, inserted after small step 1 of media): `web_search` and `webread` in the VM; see [Web search](../design/tools.md#web-search).
14. **Import** (done 2026-10-29): `max-import`, first rehearsed by importing into a temporary database, then the real import with about 12 minutes of downtime; see [Import](../design/ledger.md#import). The gateway's Resume information was in the database that was replaced, so messages sent in the groups during the downtime were not redelivered.

## Media, in six steps

The work was done in six small steps (steps 4 and 5 were added 2026-10-29):

1. The content store, `media` and `message_media`, and the download worker; inbound nodes carry the URL.
2. The model's `input`, images in entries, lowering for both protocols, attached images and handles.
3. The caption worker, with a separate prompt for stickers; import of the old image descriptions and stickers. Went live 2026-10-29: the model is GPT-5.6 Luna via cliproxy, at effort low; the old descriptions were imported before the new maxx started (21,040 images and 3,421 stickers, 94 of them SKIP), and the startup sweep filled in 10 images missed in the last 14 days.
4. Sending images: qqbot's upload, image sending and the `file_info` cache in the sender, the segmenter keeping handles and their resolution at ledger entry, and `send_image`. Went live 2026-10-29 and tested live in the group: handles written in replies sent a JPEG and a GIF sticker (the GIF animates), and `send_image` sent a PNG drawn in the VM, with a caption.
5. The sticker library: embeddings and `find_stickers`. Done 2026-10-29; see `max.find_stickers` under [Sending images](../design/media.md#sending-images).
6. Reading media in the records, and `max.image()`. `max.image()` accepting images under `/work` was done 2026-10-29; `/chat` was replaced by `max.file()`, done the same day (see [Reading files](../design/media.md#reading-files)). Accepting message handles is not yet done for `tools.show` (`max.image()` until 2026-11-14); for now, a file is first copied out with `tools.file` and then its path is passed.
