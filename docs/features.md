# Feature reference

The full behaviour of the bot, section by section. Max reads this file through
`inspect_source` (it ships in the embedded source snapshot, navigated by the
`self-knowledge` skill). For a short summary see the [README](../README.md);
for internals see [architecture.md](architecture.md).

- **Durable work continuity.** Every admitted turn receives a conversation-scoped `t#` handle and journals effects before execution. Finished turns atomically capture the exact ledger `ingest_seq` boundary used for later ambient-delta rendering. Reply-targeted continuations get deterministic journal/output/sandbox digests and, when provider family, prompt, tool catalog, archive TTL and token budget still match, a bounded verbatim provider-wire replay. Durable editable plans add typed orchestration, parallel child turns, steering, suspension, crash recovery and wake-up admission; `JoinAll` and `on-failure` are the only currently accepted join/watch policies.
- **Typed monitors.** Reminder tools are compatibility sugar over durable `TimeCron` monitors. Authorized callers can also arm intent-carrying `TimeCron` and live-ingress `LedgerMatch` monitors, addressed as `m#`; fires are deduplicated, capped, role-revalidated and admitted as ordinary recoverable turns with provenance. External HTTP polling and the admin monitor projection remain deferred.
- **Sandbox isolation.** Per-group `/work` volumes survive process restarts and expire after 14 days of inactivity. Long-lived shells are fixed-image, non-root, networkless, capability-free, resource-capped and read-only outside `/work` plus bounded tmpfs mounts. Package names are strictly bounded and realized through a short-lived host-generated Nix helper with network access; the caller's command never runs there. Command output is streamed and hashed, with 16-KiB previews and bounded 8-MiB-per-stream spill files.
- **Attachment fan-out and QQ best-effort recovery.** Matrix and iMessage accept up to eight native attachments in one canonical delivery and emit them as ordered one-media wire events, with partial-send ambiguity parked rather than replayed. On each QQ reverse-WebSocket reconnect, an in-queue barrier gives already registered group and friend endpoints a bounded latest-plus-anchor message-history pass before that generation's live events are ingested. Historical rows enter the canonical ledger oldest-first as `Backfill`, deduplicate on native event identity, enqueue media work, and never dispatch or mirror as fresh conversation. Endpoint count, page size, action calls and total time are capped; the reconnect second is left to the live stream. Every attempted endpoint gets a `qq_backfill_runs` audit row. NapCat supplies neither a durable cursor nor complete offline notices, so this remains observable `best-effort-messages-only`, not exactly-once continuity: reactions, recalls, messages outside the returned windows and malformed rows may still be absent.
- **Persistence.** Every message goes to Postgres (segments, rendered text, sender names, reply links); images and videos are stored content-addressed on disk, forwarded chats expanded into child rows.
- **Canonical multi-platform conversations.** QQ, Matrix, and iMessage normalize into one immutable message/event ledger with exact native provenance, crash-recoverable dispatch, and a leased per-endpoint delivery outbox. An explicitly configured QQ/Matrix pair shares one conversation and renders every semantic message once; transport echoes only confirm deliveries. The configured iMessage group is standalone and cannot link by name. Matrix `/sync` and `imsg` ROWID cursors advance only after durable ingest; limited Matrix timelines and replaced iMessage databases are repaired before publication. Matrix transaction IDs are deterministic, while ambiguous QQ/iMessage sends are parked for echo/status reconciliation instead of blindly retried. Inbound media is bounded and imported into BlobStore (homeserver size metadata is advisory; the bounded response is authoritative); outbound Matrix media uses native uploads and iMessage uses authenticated one-shot bridge staging with text fallback. The Mac bridge exposes only one allowlisted chat and never exposes host attachment paths. Prompt output actions generally come from the intersection of enabled endpoint capabilities. Semantic mentions are lowered per endpoint instead: QQ receives a native mention and text-only mirrors receive `@username`; QQ faces and actions without a faithful fallback remain QQ-only and are never guessed from numeric compatibility IDs. `GET /api/platforms/status` reports cursors, capabilities, backlog, and uncertain sends.
- **Triggering.** @-mention or reply in groups, everything in private chats; a 戳一戳 aimed at the bot wakes it too (the prompt says who poked — while a turn is running it lands as a nudge in that turn instead). `!` messages are commands; the rest start an async agent turn with token-budgeted chronological context, pins and memories.
- **Proactive triggering** (optional). With `intent.profile` configured, unaddressed group chatter is batched through a cheap intent classifier behind a heuristic gate (name mention or a 3-min post-dispatch hot window classify immediately; plain chatter gets at most one classification per group per 15 min — ~4x fewer classifier calls, tuned on production logs) — name-calls without an @, follow-ups to what the bot just said, topics it can help with — and may start a turn on its own. Topic barge-ins respect a per-group cooldown (name-calls and follow-ups don't), an hourly cap covers everything, `!proactive on/off` toggles per group, and the main model can still answer `[silence]`.
- **Private chats** reuse the group pipeline (chat with user *u* = group `-u`), so sessions, memories, sandboxes and commands work the same in both.
- **Agent loop.** Multi-turn tool calling with `!kill` cancellation, mid-task notes, progress narration: the model's own text alongside its tool calls is posted as it works (both wire formats allow text and tool calls in one message), `!debug` tool-call echo, a tool-result context budget, and a forced final answer at the turn cap. Two turns running at once no longer answer each other's questions: a trigger some other dispatch is already handling is marked as taken in the prompt, so the second turn doesn't helpfully answer it as well and leave one person answered twice. While a dispatch runs, the trigger message wears a 托腮 reaction (cleared when the reply lands); if the dispatch fails (upstream API error), no error text is posted — the reaction flips to /裂开 instead, and only after an interactive reply call has ridden the 2/8/20/45/90-second retry schedule. Ordinary buffered background calls use only 2/8 seconds. Historian overrides both policies because its durable queue owns retries (see Memory). Transient-looking 4xx from relay gateways ("Error from provider …: Upstream request failed") retry like a 5xx; genuine bad requests still fail fast. On a direct trigger a bare `[silence]` posts nothing and reacts 闭嘴 onto the trigger automatically (mechanism, not prompt pressure); `[silence:表情名]` swaps in any curated face for actual nuance. Leading quote handles don't break the match — `[↩#id] [silence]` is still a silence, and a reply that is nothing but a quote handle counts too.
- **Concurrent tasks and addressed feedback.** Long work uses durable `task#` identities and `task_start/status/list/steer/replace/cancel`; a bounded conversation frontend answers short questions and yields immediately after delegation. Background tasks use the existing agent runtime but do not speak independently. Results and questions return to the parent/frontend. Same-author messages and unrelated questions are never automatically merged into the newest task. `!btw <text>` remains a separate durable request, queued if the frontend is busy rather than dropped. `!task steer task#N <note>` and replies to task-linked output append attributed durable events; `!feedback`/`!fb` work only with an explicit task handle or task-linked reply. Initiators and administrators may replace/cancel; other members may suggest evidence without those powers. `!ps`/`!kill` still inspect/control process-local execution, while task tools and the admin durable-work view expose logical work across restart. Canonical output and per-endpoint outboxes remain independent of task execution. See [ADR008](adr/008-durable-tasks-conversation-coordination.md) and the [cutover runbook](runbooks/task-cutover.md) for bounds and validation.
- **Prompt shape and budget.** The whole conversation is one system message plus one user message: P1/P2/P3/P4 episode compartments precede a protected raw tail in one chronological stream, and every raw line is `[HH:MM <name> #<msgid>]: …` (Max's own lines say `Max`). Roles are not used for flat group history because `user` conflates N speakers and `assistant` drops who Max was talking to. There is no message-count window, mention-history lane, development allowlist, or session context anchor. Omitted profile limits default to 114,688 input tokens, 16,384 output tokens, and 16,384 tokens each for tool-round and multimodal attachment reserves. The raw-tail watermarks remain model-derived for smaller profiles but are capped at 16,384/32,768 tokens, so future 256K+ windows improve total headroom without making a noisy verbatim tail grow forever. A pure `ContextPolicy` produces a deterministic `ContextPlan`, token estimate, and per-source decision trace before rendering. Under pressure it removes active semantic memories first, degrades old compartments, then removes the oldest unpinned raw rows, with explicit reply targets, pins, the current trigger, environment, and attachments protected. Before the first compartment the immutable raw ledger supplies the newest rows up to the raw-tail token target; materialization failure retains the newest gap-free active projection plus its exact token-bounded raw tail without mutating either. `!clear` remains a separate user-decided floor. A question another live turn is already answering is omitted rather than annotated, preventing duplicate replies. `history_as_turns: true` on a profile switches raw history to real `user`/`assistant` turns for live comparison.
- **Memory.** Per-group and per-user memories are proposed alongside P1/P2/P3 history by the **episode Historian**. It reads the oldest token-sized raw-ledger prefix after a conversation-scoped `ingest_seq` cursor, capped at 65,536 source tokens per episode; larger backlogs become exact adjacent capture runs. A validated transaction publishes the compartment and accepted proposals together, while failures leave the CAS cursor unchanged. Historian uses `memory.timeout_seconds` (default 600 seconds) independently of the interactive profile timeout and makes one HTTP attempt per generation/repair call; its durable run retries after 1m/5m/15m/1h/6h. Fresh pending ranges are claimed before due retries, so one poison range cannot starve new episodes. One malformed structured response gets a bounded schema-repair turn; semantic omissions still use that durable retry path. Startup also backfills pre-deployment raw gaps oldest-first in token-sized, non-overlapping ranges without rewinding the live cursor. A **nightly dream pass** (4am local) walks recently touched scopes holding 15+ entries with each current version's source evidence attached. It may update a keeper and supersede overlapping or contradicted entries, archive a clearly expired entry without a replacement, and rewrite relative dates; insufficient evidence means no mutation. Each operation appends a scoped version, maintenance evidence, and audit event, and automatic maintenance cannot change permanent memories. Embedding backfill and memory maintenance use separate durable fencing-lease domains. The model's memory tools remain for explicit "记住X" requests; `!memory` audits only the current conversation. 30 entries × 300 chars per scope; the prompt injects only the 12 most recently touched per scope (framed as possibly stale, with `context_search`/`memory_list` for the long tail). **Nothing crosses conversations**: user memories are confined to the group they were learned in (`source_group_id`), and all recall paths apply the current conversation policy in SQL.
- **Unified recall and vector search** (embeddings optional). `context_search` is the model's single recall entry point. It searches scoped memories, episode summaries, raw messages, pins, and image/video captions with lexical + compatible pgvector candidates, provenance-aware deduplication, and source quotas; an episode result expands through `context_expand`. Embedding failure degrades unified recall to lexical results; no recall is automatically injected into every turn. The legacy `search_messages` and `memory_search` tools are no longer registered, avoiding ambiguous routing and placeholder filters that can silently suppress semantic results.
- **Context operations.** The authenticated admin panel has an `上下文` console for exact coverage/cursor lag, capture leases and validation, compartment/materialization state, prompt token and tier decisions, complete memory provenance, embedding spaces/backlog, and policy-scoped retrieval traces. It can enqueue full or single-compartment rebuilds, reindex selected derived vectors, and recompute integrity without rewriting source messages. Prompt traces contain decisions only (no duplicate prompt body), rebuild keeps last-known-good active until publication, and reindex is fenced against the embedding worker. `context.force_raw_fallback` is the one global release rollback: it forces token-budgeted raw-ledger prompts while preserving every projection and background job.
- **LLM profiles.** Multiple profiles, OpenAI-compatible or Anthropic-native, switched with `!model`.
- **Streaming** (on by default; `stream: false` per profile to opt out). Reads the completion over SSE and sends each paragraph the model has finished with, instead of waiting for the whole answer. The trailing paragraph is always held back — it may still grow — so a one-paragraph reply, which is most of them, is unaffected; the win is on long multi-part answers, which are also where the wait hurts. A stream that dies mid-reply leaves the fragment standing and appends `⚠ 断了，上面这条没写完`, so the reader knows it broke rather than reading a sentence that just stops. The switch is per-profile purely as an escape hatch for a provider whose SSE dialect misbehaves; replaying the assistant turn is not a reason to use it, since both protocols are designed so a stream reconstructs the message the non-streamed call would have returned — reasoning and thinking blocks included.
- **Share cards.** QQ lightapp `json` segments parse into `[card: 来源 | 标题 | 简介 | 链接]` lines instead of an opaque `[json]`; bilibili links (full URL / BV / b23.tv, from cards or plain text) feed `view_bilibili`.
- **Images.** Multimodal profiles get the images the user is pointing at (trigger / quoted message / pins) inline. Other history images render as `[image#id]` markers loaded on demand with `view_image`, so unrelated group pictures don't distract the model. QQ image URLs survive durable dispatch even though OneBot uses `url` inbound and `file` in the persisted outbound-compatible shape; blank NapCat summaries become explicit media markers and migration backfill recreates missing fetch jobs. Avatars via `view_avatar`.
- **Group awareness.** The prompt carries group name, owner and admins; `group_members` pages through the full roster.
- **Browser** (multimodal profiles). A lightweight camoufox container is reused per group, but every turn/subagent gets an independent MCP client, browser session, and state lock. Sibling subagents can navigate concurrently without changing each other's page; operations on one page remain ordered. Tools include navigate, snapshot, click, type, and scroll — snapshots list interactive elements with CSS selectors.
- **Replies.** Blank-line paragraphs go out as separate messages (fences never split; an explicit [split] marker forces a break, and a ceiling of ten bounds a runaway generation); progress narration and image captions go through the same planner and the same placeholder parsing. That sharing is load-bearing: every sender that has ever kept a private copy of "turn model text into messages" leaked a raw `[split]` or `[↩#id]` into the group. Message handles accept the foreign platform's reserved negative compatibility IDs, while face and sticker IDs stay positive-only. A reply publishes its canonical relation atomically, then each endpoint resolves the target to its native event ID. Matrix reply notifications name the relay account in `m.mentions`; Max ignores that implicit transport mention and wakes only when the canonical target is bot-authored or the visible reply explicitly mentions Max. iMessage advertises native replies only while its optional injected IMCore helper passes a live probe; `reply_to` then creates the native relation, while a missing helper fails closed into durable retry. Native-reply sends ignore IMCore's best-effort immediate GUID and wait for the authoritative database echo; ordinary sends stay on AppleScript. The public SIP-safe path emits ordinary text and never exposes `[↩#id]`, `[face#id]`, or a fake quote prefix. The execution boundary also strips any unsupported action hallucinated from an old prompt or cached skill. Conversations with a QQ endpoint retain structural `[@#qq]` mentions and the QQ-id-to-name table (group card over nickname); canonical publication preserves both target and display so QQ gets native mention behavior while text mirrors degrade to `@username`. QQ-only conversations additionally retain the permissive sticker-caption resolver.
- **Tools** (per config): the always-available `inspect_source` reads a bounded, allowlisted text snapshot embedded at compile time (`tree`/literal `search`/numbered `read`) and reports its git revision plus bundle hash; it cannot read arbitrary host files, runtime config, secrets, or database state. Other tools include `web_search` · files · sandbox (persistent per-group Docker workspace; a roughly Ubuntu-default base userland on PATH, anything beyond it pulled per-command from pinned nixpkgs) · memory · unified `context_search` / `context_expand` recall · `group_members` / `view_avatar` / `view_image` / `view_forward` / `view_video` (multimodal: whole video inline via the `video_url` block extension) / `view_bilibili` (metadata + top comments; `with_video` streams the 480p MP4 inline) / `poke` · browser. Source defaults describe the binary but never prove the production effective configuration. Tool descriptions carry only the call-time contract; the operating manuals live behind `use_skill` (see Skills).
- **Skills.** Progressive disclosure sized for a chat bot: the system prompt carries one byte-stable index line per skill (name + description), and `use_skill` fetches the body as a tool result — so a group with twenty skills never pays twenty bodies. Three sources, name-shadowed group > DB-global > builtin: **builtin** skills ship inside the binary (`skills/*.md`), **global** and **per-group** rows live in the `skills` table, editable at runtime via the admin API, so a DB row hot-fixes a shipped skill without a release. `self-knowledge` is the single self-inspection entry point: a navigation map over the embedded source snapshot (behaviour, architecture, ADRs, schema and code are all read via `inspect_source`, never mirrored into skill bodies) plus two runtime-generated splices at registry init: the live `!help` text and the build-identity half of the `!version` card (version + git rev, distro/arch, ghc/cabal — the part that is fixed for the process; uptime and per-group tool/skill counts stay live in the command) — so what the bot tells users, what it knows about itself, and what it can prove from source are the same values. Builtin manuals so far: `self-knowledge` · `sandbox` (nix workflow, output spill, file exchange, CJK fonts) · `web` (bilibili/zhihu/browser) · `office` (pdf/docx/xlsx/pptx recipes). DB skill bodies are capped at 49,152 characters; the `use_skill` tool registers only when the group has skills visible.
- **Pins.** Messages worth keeping in every prompt (specs, decisions, reference images) survive `!clear`. Curated by the model itself via `pin_message`/`unpin_message` tools; `!pin`/`!unpin`/`!pins` remain as the manual override.
- **Commands**: `!help`, `!model`, `!debug`, `!persona`, `!proactive`, `!sticker`, `!clear`, `!unclear`, `!pin`/`!unpin`/`!pins`, `!memory`, `!btw`, `!feedback`/`!fb`, `!ps`, `!kill`, `!status`, `!version` (version + short git rev, `x tools · y skills` as this group sees them, uptime), `!use`, and `! <shell>` (runs in the group's sandbox). In a group, textual output goes to the sender's DMs and the group only sees an OK reaction.
- `@bot ping` → `pong`, no LLM call.
- **Admin JSON API** (config `admin.port`; absent = off). A loopback warp server inside the bot process — inside because half the state is in-process: sessions are a write-through cache (a row edited behind the registry's back is a row the bot never sees), running turns live in the task registry. Read: `GET /api/overview` (version, git rev, uptime) `· /api/groups · /api/memories?scope=group|user&id=… · /api/skills[?group=…] · /api/tasks · /api/usage?days=N · /api/quota · /api/stats/messages?days=N · /api/logs · /api/calls`. Write: `PATCH /api/groups/:gid/session` (model/effort/persona/debug/sticker/proactive; `null` clears an override), `POST/PATCH/DELETE /api/skills` (builtins are read-only — shadow them with a same-name row instead), `DELETE /api/memories/:id`, `DELETE /api/tasks/:tid` (kill). Auth is an optional bearer token — TLS/SSO belong to the reverse proxy in front. The caller is owner-tier by definition: whoever reaches the port can edit max.yaml.
- **Token accounting** (`llm_usage`, migration 030). Every completed LLM call books one row — group (NULL for the caption workers' shared pool), source (`turn`/`wrapup`/`intent`/`supplement`/`historian`/`memory-dream`/`caption`), profile, prompt/completion/cached tokens. Attribution and optional per-call timeout/retry overrides ride the typed `ChatCtx` on every `chat` call, so the compiler keeps both policies explicit; the eval harness writes nowhere. `/api/usage` serves daily aggregates with day boundaries in the configured timezone.
- **Subscription health** (config `cliproxy.management_key`; absent = `/api/quota` answers `configured: false`). When the LLM `base_url` is a [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) holding OAuth credentials rather than a plain API key, the question "is the subscription still serving" has its answer in another process. `GET /api/quota` asks that process: per credential, provider and plan tier, whether it is `serving` (the proxy spreads that over `status`/`disabled`/`unavailable`, so the endpoint collapses it), `next_retry_after` for a burnt one, lifetime success/failure counts, and the proxy's twenty 10-minute traffic buckets totalled. Upstream unreachable answers 502, not an empty pool — "no credentials" and "can't tell" are different sentences. The proxy needs `remote-management.secret-key` set on its side; without it the 404 comes back saying so. What this deliberately doesn't claim to know is how much of the ChatGPT 5-hour and weekly windows is left: Codex reports that in response headers, and CLIProxyAPI neither reads nor forwards them — it learns a credential is spent by being told `usage_limit_reached`, after the fact. So this is a warning light, not a fuel gauge.
