# Feature reference

The full behaviour of the bot, section by section. For a short summary see the
[README](../README.md); for internals see [architecture.md](architecture.md).

- **Persistence.** Every message goes to Postgres (segments, rendered text, sender names, reply links); images and videos are stored content-addressed on disk, forwarded chats expanded into child rows.
- **Triggering.** @-mention or reply in groups, everything in private chats; a 戳一戳 aimed at the bot wakes it too (the prompt says who poked — while a turn is running it lands as a nudge in that turn instead). `!` messages are commands; the rest start an async agent turn with recent context, prior bot conversations, pins and memories.
- **Proactive triggering** (optional). With `intent.profile` configured, unaddressed group chatter is batched through a cheap intent classifier behind a heuristic gate (name mention or a 3-min post-dispatch hot window classify immediately; plain chatter gets at most one classification per group per 15 min — ~4x fewer classifier calls, tuned on production logs) — name-calls without an @, follow-ups to what the bot just said, topics it can help with — and may start a turn on its own. Topic barge-ins respect a per-group cooldown (name-calls and follow-ups don't), an hourly cap covers everything, `!proactive on/off` toggles per group, and the main model can still answer `[silence]`.
- **Private chats** reuse the group pipeline (chat with user *u* = group `-u`), so sessions, memories, sandboxes and commands work the same in both.
- **Agent loop.** Multi-turn tool calling with `!kill` cancellation, mid-task notes, progress narration: the model's own text alongside its tool calls is posted as it works (both wire formats allow text and tool calls in one message), `!debug` tool-call echo, a tool-result context budget, and a forced final answer at the turn cap. Two turns running at once no longer answer each other's questions: a trigger some other dispatch is already handling is marked as taken in the prompt, so the second turn doesn't helpfully answer it as well and leave one person answered twice. While a dispatch runs, the trigger message wears a 托腮 reaction (cleared when the reply lands); if the dispatch fails (upstream API error), no error text is posted — the reaction flips to /裂开 instead, and only after the reply call has ridden out ~3 minutes of backoff (relay outages come in minutes-long windows; background classifier calls keep a 10-second schedule so they never stall a dispatch). Transient-looking 4xx from relay gateways ("Error from provider …: Upstream request failed") retry like a 5xx; genuine bad requests still fail fast. A `[silence:表情名]` reply on a direct trigger posts nothing but reacts the named reason face (擦汗/流汗/再见/哈欠/吃瓜/困/疑问) onto the trigger.
- **Interrupting a running turn.** Two things you might mean, so two commands. `!feedback <text>` (alias `!fb`) hands a note to a turn that is already running — reply to that turn's trigger message to pick which one, or say nothing and it goes to the newest; the agent loop drains its inbox between tool rounds, so the note lands mid-work rather than after. `!btw <text>` is the opposite: a quick side question that deliberately leaves the running turn alone, answered in its own parallel turn — ordinary in every other way (reply persisted, memory live), except that the intent classifier is not allowed to overrule you and fold it into the running turn after all. Anyone can feed anyone's turn — notes are rendered like history lines (`[#id] <name>: text`), so the model can see who said what and answer them by name. Implicitly, a message arriving during a running turn is intent-classified into the same two buckets: reads as steering → absorbed as feedback, reads as a new question → its own dispatch. That covers unaddressed messages too — a proactive followup ("不对，改成X" without an @) steers the running turn instead of talking over it — and the implicit path aims the same way `!feedback` does: replying to a running turn's trigger sends the note to that turn, not whichever started last. A note that lands (explicit or implicit) wears the same 托腮 the turn's own trigger does, taken off when the absorbing turn ends. A misaimed `!feedback` (mis-click, a turn that has since finished) falls back to the newest turn rather than erroring — a note that refuses to land ends up in nobody's context at all — and `!feedback` with nothing running at all is answered as an ordinary turn instead of being dropped (except under a `!use` redirect, where a DM turn isn't the group task you were steering: that keeps the failure face). `!ps` shows each turn's trigger id (`on=#…`) and pending note count (`fb=…`); a 戳一戳 during a running turn is a contentless nudge into it. The `messages` table mirrors the group exactly — every line the bot actually said is recorded, including progress narration, `!debug` tool traces and command replies — and each row carries a `kind` (`chat` / `command` / `debug`) that decides whether the prompt shows it. So `!ps`/`!model`/`!memory rm 3` and the `⚙`/`↳` debug trace stay out of the model's view (and out of `search_messages`) while remaining in the record for forensics and `!clear`. `!btw` and `!feedback` are the exception: their bodies are things somebody said to the bot and the bot answers them, so they record as `chat` with the verb stripped — the same shape the implicit supplement path already stores.
- **Prompt shape.** The whole conversation is one system message plus one user message: the group's recent chatter and the bot's own past replies are interleaved into a single chronological transcript, each line `[HH:MM <name> #<msgid>]: …` (the bot's own lines say `Max`). Roles are not used for history because they can't express a group — `user` conflates N speakers and `assistant` drops who the bot was answering; a line that names its speaker, time and id carries strictly more, and every model reads it because it is just text. Two history queries feed it (last 40 messages, and last 40 that involve the bot) merged and deduped, so a busy group can't push the bot's own thread out of its memory. Falls out of this: consecutive same-role messages are structurally impossible, and prior bot replies no longer sit in the `assistant` slot for a weak model to continue as a pattern. A question some other turn is already answering is dropped from the prompt rather than annotated — the model can't double-answer what it can't see, and the annotation this replaced got emitted verbatim as a reply. `history_as_turns: true` on a profile switches back to real `user`/`assistant` turns (consecutive same-side rows merged, bot turns unlabelled) so the two shapes can be compared with `!model` rather than argued about.
- **Memory.** Per-group and per-user memories injected into the system prompt; written by the model's memory tools and a post-reply extractor, audited with `!memory` — which in a DM still lists everything the bot knows about you, tagged by the conversation each fact came from, since that is now the only place to see the whole record. 30 entries × 300 chars per scope. **Nothing crosses conversations**: user memories are confined to the group they were learned in (`source_group_id`), and `memory_search` only ranks the current group's rows — the extractor reads group context, so without this a fact picked up from one group's chatter rode along into every other group that person appeared in.
- **Vector search** (optional). A worker embeds messages and memories into pgvector; enables semantic `search_messages` and `memory_search` (scoped to the current group). Falls back to substring/regex without it.
- **LLM profiles.** Multiple profiles, OpenAI-compatible or Anthropic-native, switched with `!model`.
- **Streaming** (on by default; `stream: false` per profile to opt out). Reads the completion over SSE and sends each paragraph the model has finished with, instead of waiting for the whole answer. The trailing paragraph is always held back — it may still grow — so a one-paragraph reply, which is most of them, is unaffected; the win is on long multi-part answers, which are also where the wait hurts. A stream that dies mid-reply leaves the fragment standing and appends `⚠ 断了，上面这条没写完`, so the reader knows it broke rather than reading a sentence that just stops. The switch is per-profile purely as an escape hatch for a provider whose SSE dialect misbehaves; replaying the assistant turn is not a reason to use it, since both protocols are designed so a stream reconstructs the message the non-streamed call would have returned — reasoning and thinking blocks included.
- **Share cards.** QQ lightapp `json` segments parse into `[card: 来源 | 标题 | 简介 | 链接]` lines instead of an opaque `[json]`; bilibili links (full URL / BV / b23.tv, from cards or plain text) feed `view_bilibili`.
- **Images.** Multimodal profiles get the images the user is pointing at (trigger / quoted message / pins) inline. Other history images render as `[image#id]` markers loaded on demand with `view_image`, so unrelated group pictures don't distract the model. Avatars via `view_avatar`.
- **Group awareness.** The prompt carries group name, owner and admins; `group_members` pages through the full roster.
- **Browser** (multimodal profiles). Per-group camoufox container (stealth Firefox over MCP): navigate, snapshot, click, type, scroll — snapshots list interactive elements with CSS selectors.
- **Replies.** Blank-line paragraphs go out as separate messages (fences never split; an explicit [split] marker forces a break, and a ceiling of ten bounds a runaway generation); progress narration splits the same way — it used to be the one sender that took neither marker and leaked `[split]` as literal text. A QQ-id-to-name table in the prompt keeps names straight, group card over nickname.
- **Tools** (per config): `web_search` · files · sandbox (persistent per-group Docker workspace, packages from pinned nixpkgs) · memory · message search · `group_members` / `view_avatar` / `view_image` / `view_forward` / `view_video` (multimodal: whole video inline via the `video_url` block extension) / `view_bilibili` (metadata + top comments; `with_video` streams the 480p MP4 inline) / `poke` · browser.
- **Pins.** Messages worth keeping in every prompt (specs, decisions, reference images) survive `!clear`. Curated by the model itself via `pin_message`/`unpin_message` tools; `!pin`/`!unpin`/`!pins` remain as the manual override.
- **Commands**: `!help`, `!model`, `!debug`, `!persona`, `!proactive`, `!sticker`, `!clear`, `!unclear`, `!pin`/`!unpin`/`!pins`, `!memory`, `!btw`, `!feedback`/`!fb`, `!ps`, `!kill`, `!status`, `!version`, `!grant`/`!revoke`/`!perms`, `!use`, and `! <shell>` (runs in the group's sandbox). In a group, textual output goes to the sender's DMs and the group only sees an OK reaction.
- `@bot ping` → `pong`, no LLM call.
