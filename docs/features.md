# Feature reference

The full behaviour of the bot, section by section. For a short summary see the
[README](../README.md); for internals see [architecture.md](architecture.md).

- **Persistence.** Every message goes to Postgres (segments, rendered text, sender names, reply links); images and videos are stored content-addressed on disk, forwarded chats expanded into child rows.
- **Triggering.** @-mention or reply in groups, everything in private chats; a 戳一戳 aimed at the bot wakes it too (the prompt says who poked — while a turn is running it lands as a nudge in that turn instead). `!` messages are commands; the rest start an async agent turn with recent context, prior bot conversations, pins and memories.
- **Proactive triggering** (optional). With `intent.profile` configured, unaddressed group chatter is batched through a cheap intent classifier behind a heuristic gate (name mention or a 3-min post-dispatch hot window classify immediately; plain chatter gets at most one classification per group per 15 min — ~4x fewer classifier calls, tuned on production logs) — name-calls without an @, follow-ups to what the bot just said, topics it can help with — and may start a turn on its own. Topic barge-ins respect a per-group cooldown (name-calls and follow-ups don't), an hourly cap covers everything, `!proactive on/off` toggles per group, and the main model can still answer `[silence]`.
- **Private chats** reuse the group pipeline (chat with user *u* = group `-u`), so sessions, memories, sandboxes and commands work the same in both.
- **Agent loop.** Multi-turn tool calling with `!kill` cancellation, mid-task notes, progress narration: the model's own text alongside its tool calls is posted as it works (both wire formats allow text and tool calls in one message), `!debug` tool-call echo, a tool-result context budget, and a forced final answer at the turn cap. Two turns running at once no longer answer each other's questions: a trigger some other dispatch is already handling is marked as taken in the prompt, so the second turn doesn't helpfully answer it as well and leave one person answered twice. While a dispatch runs, the trigger message wears a 托腮 reaction (cleared when the reply lands); if the dispatch fails (upstream API error), no error text is posted — the reaction flips to /裂开 instead, and only after the reply call has ridden out ~3 minutes of backoff (relay outages come in minutes-long windows; background classifier calls keep a 10-second schedule so they never stall a dispatch). Transient-looking 4xx from relay gateways ("Error from provider …: Upstream request failed") retry like a 5xx; genuine bad requests still fail fast. On a direct trigger a bare `[silence]` posts nothing and reacts 闭嘴 onto the trigger automatically (mechanism, not prompt pressure); `[silence:表情名]` swaps in any curated face for actual nuance. Leading quote handles don't break the match — `[↩#id] [silence]` is still a silence, and a reply that is nothing but a quote handle counts too.
- **Interrupting a running turn.** Two things you might mean, so two commands. `!feedback <text>` (alias `!fb`) hands a note to a turn that is already running — reply to that turn's trigger message to pick which one, or say nothing and it goes to the newest; the agent loop drains its inbox between tool rounds, so the note lands mid-work rather than after. `!btw <text>` is the opposite: a quick side question that deliberately leaves the running turn alone, answered in its own parallel turn — ordinary in every other way (reply persisted, memory live), except that the intent classifier is not allowed to overrule you and fold it into the running turn after all. Anyone can feed anyone's turn — notes are rendered like history lines (`[#id] <name>: text`), so the model can see who said what and answer them by name. Implicitly, a message arriving during a running turn is intent-classified into the same two buckets: reads as steering → absorbed as feedback, reads as a new question → its own dispatch. That covers unaddressed messages too — a proactive followup ("不对，改成X" without an @) steers the running turn instead of talking over it — and the implicit path aims the same way `!feedback` does: replying to a running turn's trigger sends the note to that turn, not whichever started last. A note that lands (explicit or implicit) wears the same 托腮 the turn's own trigger does, taken off when the absorbing turn ends. A misaimed `!feedback` (mis-click, a turn that has since finished) falls back to the newest turn rather than erroring — a note that refuses to land ends up in nobody's context at all — and `!feedback` with nothing running at all is answered as an ordinary turn instead of being dropped (except under a `!use` redirect, where a DM turn isn't the group task you were steering: that keeps the failure face). `!ps` shows each turn's trigger id (`on=#…`) and pending note count (`fb=…`); a 戳一戳 during a running turn is a contentless nudge into it. The `messages` table mirrors the group exactly — every line the bot actually said is recorded, including progress narration, `!debug` tool traces and command replies — and each row carries a `kind` (`chat` / `command` / `debug`) that decides whether the prompt shows it. So `!ps`/`!model`/`!memory rm 3` and the `⚙`/`↳` debug trace stay out of the model's view (and out of `search_messages`) while remaining in the record for forensics and `!clear`. `!btw` and `!feedback` are the exception: their bodies are things somebody said to the bot and the bot answers them, so they record as `chat` with the verb stripped — the same shape the implicit supplement path already stores. **A note leaves the inbox only by entering the conversation**: one the turn accepted but never served (it raced an already-streamed answer) goes back to the inbox, surfaces when the task ends, and — when it carries its source message — is re-dispatched as a turn of its own, so an absorbed @-mention can't die unanswered. A `!kill`ed turn keeps nothing: kill means stop, notes included.
- **Prompt shape and budget.** The whole conversation is one system message plus one user message: group chatter and Max's past replies are interleaved into one chronological transcript, each line `[HH:MM <name> #<msgid>]: …` (Max's own lines say `Max`). Roles are not used for flat history because they cannot express a group: `user` conflates N speakers and `assistant` drops who Max was talking to. During the compartment migration, two legacy queries still feed this stream—the most recent messages and older messages that involve Max—and the existing `history_window` / `history_max` count watermark still provides a cache-friendly compatibility fold. It is no longer the model-window safety boundary. The selected profile supplies `max_input_tokens`, output, attachment, and tool-round reserves; a pure `ContextPolicy` produces a deterministic `ContextPlan`, token estimate, and per-source decision trace before rendering. Under pressure it removes active semantic memories first, then the oldest unpinned raw rows, with explicit reply targets, pins, the current trigger, environment, and attachments protected. The dual query/count fold will be removed once exact compartment coverage and the token-budgeted protected tail are serving prompts. `!clear` remains a separate user-decided floor. A question another live turn is already answering is omitted rather than annotated, preventing duplicate replies. `history_as_turns: true` on a profile switches to real `user`/`assistant` turns for live comparison.
- **Memory.** Per-group and per-user memories are proposed alongside P1/P2/P3 history by the **episode Historian**. It reads the oldest token-sized raw-ledger prefix after a conversation-scoped `ingest_seq` cursor; a validated transaction publishes the compartment and accepted proposals together, while failures leave the CAS cursor unchanged. One malformed structured response gets a bounded schema-repair turn; semantic omissions still use the durable retry path. The legacy extractor remains only until final coverage/replay cutover. A **nightly dream pass** (4am local) walks recently touched scopes holding 15+ entries with each current version's source evidence attached. It may update a keeper and supersede overlapping or contradicted entries, archive a clearly expired entry without a replacement, and rewrite relative dates; insufficient evidence means no mutation. Each operation appends a scoped version, maintenance evidence, and audit event, and automatic maintenance cannot change permanent memories. Embedding backfill and memory maintenance use separate durable fencing-lease domains. The model's memory tools remain for explicit "记住X" requests; `!memory` audits only the current conversation. 30 entries × 300 chars per scope; the prompt injects only the 12 most recently touched per scope (framed as possibly stale, with `context_search`/`memory_list` for the long tail). **Nothing crosses conversations**: user memories are confined to the group they were learned in (`source_group_id`), and all recall paths apply the current conversation policy in SQL.
- **Unified recall and vector search** (embeddings optional). `context_search` searches scoped memories, episode summaries, raw messages, pins, and image/video captions with lexical + compatible pgvector candidates, provenance-aware deduplication, and source quotas; an episode result expands through `context_expand`. `search_messages` and `memory_search` remain compatibility names that narrow this same policy to their historical corpus, while message regex/sender/time constraints retain their specialised exact query. Embedding failure degrades unified recall to lexical results; no recall is automatically injected into every turn.
- **LLM profiles.** Multiple profiles, OpenAI-compatible or Anthropic-native, switched with `!model`.
- **Streaming** (on by default; `stream: false` per profile to opt out). Reads the completion over SSE and sends each paragraph the model has finished with, instead of waiting for the whole answer. The trailing paragraph is always held back — it may still grow — so a one-paragraph reply, which is most of them, is unaffected; the win is on long multi-part answers, which are also where the wait hurts. A stream that dies mid-reply leaves the fragment standing and appends `⚠ 断了，上面这条没写完`, so the reader knows it broke rather than reading a sentence that just stops. The switch is per-profile purely as an escape hatch for a provider whose SSE dialect misbehaves; replaying the assistant turn is not a reason to use it, since both protocols are designed so a stream reconstructs the message the non-streamed call would have returned — reasoning and thinking blocks included.
- **Share cards.** QQ lightapp `json` segments parse into `[card: 来源 | 标题 | 简介 | 链接]` lines instead of an opaque `[json]`; bilibili links (full URL / BV / b23.tv, from cards or plain text) feed `view_bilibili`.
- **Images.** Multimodal profiles get the images the user is pointing at (trigger / quoted message / pins) inline. Other history images render as `[image#id]` markers loaded on demand with `view_image`, so unrelated group pictures don't distract the model. Avatars via `view_avatar`.
- **Group awareness.** The prompt carries group name, owner and admins; `group_members` pages through the full roster.
- **Browser** (multimodal profiles). Per-group camoufox container (stealth Firefox over MCP): navigate, snapshot, click, type, scroll — snapshots list interactive elements with CSS selectors.
- **Replies.** Blank-line paragraphs go out as separate messages (fences never split; an explicit [split] marker forces a break, and a ceiling of ten bounds a runaway generation); progress narration and image captions go through the same planner and the same placeholder parsing. That sharing is load-bearing: every sender that has ever kept a private copy of "turn model text into messages" leaked a raw `[split]` or `[↩#id]` into the group. The outbound grammar is liberal where models predictably slip: a caption in the sticker id slot (`[sticker#柴犬瘫地]`) resolves against the library (exact > prefix > substring, popularity as tiebreak) instead of leaking as text, and echoed display decorations (`: caption]`, `(29秒)`) are consumed. A QQ-id-to-name table in the prompt keeps names straight, group card over nickname.
- **Tools** (per config): `web_search` · files · sandbox (persistent per-group Docker workspace, packages from pinned nixpkgs) · memory · message search · `group_members` / `view_avatar` / `view_image` / `view_forward` / `view_video` (multimodal: whole video inline via the `video_url` block extension) / `view_bilibili` (metadata + top comments; `with_video` streams the 480p MP4 inline) / `poke` · browser. Tool descriptions carry only the call-time contract; the operating manuals live behind `use_skill` (see Skills).
- **Skills.** Progressive disclosure sized for a chat bot: the system prompt carries one byte-stable index line per skill (name + description), and `use_skill` fetches the body as a tool result — so a group with twenty skills never pays twenty bodies. Three sources, name-shadowed group > DB-global > builtin: **builtin** skills ship inside the binary (`skills/*.md`, plus `docs/features.md` and `docs/architecture.md` embedded verbatim as `self-features`/`self-architecture` — this very document is the bot's self-knowledge), **global** and **per-group** rows live in the `skills` table, editable at runtime via the admin API, so a DB row hot-fixes a shipped skill without a release. `self-knowledge`'s command section is the live `!help` text, spliced at registry init (`{{commands}}`) — what the bot tells users and what it knows about itself are one value. Builtin manuals so far: `self-knowledge` · `self-features` · `self-architecture` · `sandbox` (nix workflow, output spill, file exchange, CJK fonts) · `web` (bilibili/zhihu/browser) · `office` (pdf/docx/xlsx/pptx recipes). The `use_skill` tool registers only when the group has skills visible.
- **Pins.** Messages worth keeping in every prompt (specs, decisions, reference images) survive `!clear`. Curated by the model itself via `pin_message`/`unpin_message` tools; `!pin`/`!unpin`/`!pins` remain as the manual override.
- **Commands**: `!help`, `!model`, `!debug`, `!persona`, `!proactive`, `!sticker`, `!clear`, `!unclear`, `!pin`/`!unpin`/`!pins`, `!memory`, `!btw`, `!feedback`/`!fb`, `!ps`, `!kill`, `!status`, `!version` (version + short git rev, `x tools · y skills` as this group sees them, uptime), `!grant`/`!revoke`/`!perms`, `!use`, and `! <shell>` (runs in the group's sandbox). In a group, textual output goes to the sender's DMs and the group only sees an OK reaction.
- `@bot ping` → `pong`, no LLM call.
- **Admin JSON API** (config `admin.port`; absent = off). A loopback warp server inside the bot process — inside because half the state is in-process: sessions are a write-through cache (a row edited behind the registry's back is a row the bot never sees), running turns live in the task registry. Read: `GET /api/overview` (version, git rev, uptime) `· /api/groups · /api/memories?scope=group|user&id=… · /api/skills[?group=…] · /api/permissions · /api/tasks · /api/usage?days=N · /api/quota · /api/stats/messages?days=N · /api/logs · /api/calls`. Write: `PATCH /api/groups/:gid/session` (model/effort/persona/debug/sticker/proactive; `null` clears an override), `POST/PATCH/DELETE /api/skills` (builtins are read-only — shadow them with a same-name row instead), `POST/DELETE /api/permissions`, `DELETE /api/memories/:id`, `DELETE /api/tasks/:tid` (kill). Auth is an optional bearer token — TLS/SSO belong to the reverse proxy in front. The caller is owner-tier by definition: whoever reaches the port can edit max.yaml.
- **Token accounting** (`llm_usage`, migration 030). Every completed LLM call books one row — group (NULL for the caption workers' shared pool), source (`turn`/`wrapup`/`intent`/`supplement`/`memx`/`memx-compact`/`memx-dream`/`caption`), profile, prompt/completion/cached tokens. Attribution rides a `ChatCtx` parameter on every `chat` call, so the compiler keeps it honest; the eval harness writes nowhere. `/api/usage` serves daily aggregates with day boundaries in the configured timezone.
- **Subscription health** (config `cliproxy.management_key`; absent = `/api/quota` answers `configured: false`). When the LLM `base_url` is a [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) holding OAuth credentials rather than a plain API key, the question "is the subscription still serving" has its answer in another process. `GET /api/quota` asks that process: per credential, provider and plan tier, whether it is `serving` (the proxy spreads that over `status`/`disabled`/`unavailable`, so the endpoint collapses it), `next_retry_after` for a burnt one, lifetime success/failure counts, and the proxy's twenty 10-minute traffic buckets totalled. Upstream unreachable answers 502, not an empty pool — "no credentials" and "can't tell" are different sentences. The proxy needs `remote-management.secret-key` set on its side; without it the 404 comes back saying so. What this deliberately doesn't claim to know is how much of the ChatGPT 5-hour and weekly windows is left: Codex reports that in response headers, and CLIProxyAPI neither reads nor forwards them — it learns a credential is spent by being told `usage_limit_reached`, after the fact. So this is a warning light, not a fuel gauge.
