# VMs

## VM processes

Decided 2026-10-27: the Haskell version's VM design (cloud-hypervisor plus a NixOS guest) is kept, but the broker is removed, and nothing at run time requires root. Each VM was a child process of the main process until 2026-11-12; since then it is a unit of the host's systemd, `maxx-vm@<conversation>.service`, which max starts and stops and which outlives max (the second step of [Lifetimes move to systemd](../decisions/2026-11-12-lifetimes-to-systemd.md#lifetimes-move-to-systemd-1)).

The Haskell version's approach is described in [ADR 011](https://github.com/HCHogan/max/blob/a5de2e1410f5cdfaa4b88c052bd499ee8b676759/docs/adr/011-native-systemd-runtime.md) (which still used nspawn at the time): the main process had no root, and starting and stopping VMs, creating network namespaces, allocating addresses, preparing volumes, executing commands in the guest and installing packages were all delegated to a socket-activated root broker of about 1,000 lines. The VM's unit set no `User=` and ran as root.

The approach here is the same as that of microvm.nix's own host module: cloud-hypervisor runs as an ordinary user in the `kvm` group, and root creates the taps for that user in advance.

- **Only the declarative configuration applied at boot requires root**, and all of it lives in NixOS:
  - `maxx` is added to the `kvm` group.
  - A oneshot unit, `maxx-taps`, pre-creates a set of taps with `ip tuntap` (the number is configurable and defaults to 32), owned by `maxx`, with multi-queue and vnet headers enabled. systemd-networkd is not used, because the module does not choose a network stack on the host's behalf. The taps remain when this unit stops, so restarting it does not disconnect running VMs.
  - Each tap is its own /30 (carved out of `10.235.0.0/24` by default): the host end is `.1`, the guest is `.2`, and all VMs use the same MAC. Addresses are not assigned by DHCP (changed 2026-10-29; DHCP had been decided on 2026-10-27): when the main process starts a VM, it adds `max.ip`, `max.gateway`, `max.dns` and the SSH public key for this boot, `max.key`, to the guest's kernel command line, and a oneshot in the guest reads them and applies the configuration before the network comes up. No DHCP server has to run on the host, and no separate shared directory is needed for DNS and the public key.
  - The taps are not bridged; VMs are kept apart from one another by routing and nft. nft allows a VM to use only its own tap's `.2` as a source address, allows it to reach only public addresses, and forbids IPv6; connections from VMs to the host are always rejected, the host answers only established connections, and outgoing traffic is masqueraded.
- **Starting a VM:** max picks a free slot (if there is none, it stops the VM that has been unused longest and is neither in use, busy nor kept running), prepares `work` and `nix.img` under `/var/lib/maxx/vm/<conversation id>/`, binds the service's socket there, and writes three files: `boot.env`, which the unit reads (the tap, the sizes, the kernel, the initrd and the command line), `boot.json`, which the next max reads (the slot, the guest's contract, the image, whether with Max's units), and `ssh.key`, the key made for this boot. Then it has systemd start `maxx-vm@<conversation>.service` (`vm/machine.rs`), whose launcher (`nix/module.nix`) starts two virtiofsd instances (a read-only one for the store and a read-write one for `/work`) and cloud-hypervisor, the unit's main process. max then attempts an SSH connection every 100 ms; once one succeeds, the VM counts as started, with no separate readiness notification. The conversation's media view is not mounted; see [Reading files](media.md#reading-files). A polkit rule lets max's user start and stop these units and no others.
- **At least 2 vCPUs:** the tap is multi-queue, and cloud-hypervisor opens it in multi-queue mode only when there are two or more queue pairs, while each vCPU can be assigned at most one pair.
- **Each VM has a different tap name**, whereas the `microvm-run` generated by microvm.nix hard-codes the tap name at build time. Decided 2026-10-29: the cloud-hypervisor and virtiofsd command lines are max's own, and only the guest's kernel, initrd and kernel command line are borrowed, which the guest's build emits as a JSON file whose path is written into the configuration. Each VM already differs in several parameters (directories, tap, Landlock rules), and microvm.nix's runner also creates disks by itself and starts socat to forward notifications. The command lines were assembled in Rust until 2026-11-12; they are the launcher's in `nix/module.nix` now, and what differs from boot to boot comes from `boot.env`.
- **Channels:** the hybrid vsock socket lives in this directory, and the main process uses it directly. It connects to port 22 and runs russh, with one connection per VM and one channel per command; it listens for the guest's calls on `notify.vsock_7777` (see [The guest's calls](tools.md#the-guests-calls)).
- **A VM outlives max** (2026-11-12, proposed by the owner; until then a VM's lifetime was that of its process, a child of max, and every restart of max, as at each deploy, ended the VMs with the commands, agents and resident programs in them). The unit isn't part of `maxx.service`: stopping or crashing max leaves it, and `restartIfChanged = false` keeps a deploy that changes the unit from restarting it. When max starts, it lists the active `maxx-vm@` units and attaches to each (`Service::attach`): it reads `boot.json`, takes the VM's slot, binds the service's socket again (that socket alone: the VM's own are its to keep) and logs in with the saved key. The idle time counts from then. A VM it can't use is stopped, and boots again when it is next needed, at once if it is kept on: one without a record, one whose slot isn't free for it, and one whose guest keeps another contract. The contract is a number (`nix/contract.nix`) for what max says to a guest it didn't boot and what the guest keeps between images; the guest's JSON carries it. A VM booted from an image that a deploy has replaced, with the same contract, runs on, and its guest is switched to the new system where it runs (proposed by the owner): the guest's store is the host's, so the new system is already there, and max runs that image's `max-switch` in the guest (`machine::switch`, `nix/guest.nix`), which loads the system's paths into the guest's Nix database, as `register-nix-paths` does at boot from a command line that doesn't change, and then runs NixOS's `switch-to-configuration test` in a unit of its own. Commands, agents and resident programs run through it: Max's own units and the transient ones aren't in `/etc/systemd/system`, which is all a switch looks at, and what must not restart under running work is marked `restartIfChanged = false` (`max-guest`, `max-host@`, `max-notify@`, `max-browser`); the runner's link has a unit of its own, `max-runner`, which a switch runs again. The guest's JSON carries the system and its registration for this, and `boot.json` the kernel and initrd the VM booted, which no switch changes. A VM that boots another kernel or initrd than the image's, or whose switch failed, is `stale`: it is stopped once nothing of Max's runs in it and nobody has used it for 10 minutes (`rested`), so that it boots the new image whole; a kept one boots again in the same sweep. If max's connection to a VM is lost while its unit runs, as when a switch restarts sshd, max attaches again (`Service::reattach`) before it gives the VM up. If the unit doesn't run any more, the VM has ended by itself: `machine::attach` asks systemd before it tries the socket, the end counts as a failure, and the call that found it so has the VM boot again (2026-11-13; until then max tried the dead VM's socket for 10 seconds, and that call failed). max links what each VM booted, whose kernel modules it goes on loading, and each image it was switched to, whose processes may run on (`7` and `7.<the image's name>`), under `/nix/var/nix/gcroots/per-user/maxx/`, since the host's weekly collection would otherwise take a replaced image from under a running guest. The links go when max stops the VM, and those of VMs that ended without max, as when the host restarted, when max next starts (2026-11-13; until then a second switch unrooted the image of the first, and the links of such VMs stayed until their conversations booted again). While max is away, the guest's forwarder answers for it: it tries the port first, and says 503 with `max-away` if nothing listens, so that a caller knows nothing of its request was read; `client.js` makes the call again, for up to 3 minutes. max says the same itself while it stops (2026-11-13): once the table has told the actors to stop, a call that comes from a VM is begun by nobody and answered 503 with `max-away`, and the next max takes it. Until then such a call waited unread through the 25 seconds the conversations have to stop and then failed as `closed`, which nothing makes again. A call that was running when max stopped still fails as `closed`: it may have acted. A VM is stopped only by max asking systemd (idle, evicted, dead, on an older image and quiet, or unusable at attach), by `systemctl stop maxx.target`, and by vm-check, which stops its own as it ends (`Vms::shut`). A stop is `systemctl stop --no-block`, and a boot of the same VM waits until systemd has that request (`Service::stopping`): a start that reached systemd first would be the one stopped, as could happen to a kept VM stopped for a new image and started in the same sweep.
- **Getting into a VM, and the VMs in `machinectl`** (2026-11-13, asked by the owner, for debugging):
  - **`maxx-ssh 7`** on the host is a shell in conversation 7's VM, as root in the guest, and `maxx-ssh 7 systemctl status` a command there (`nix/module.nix`, on the system's path where the VMs are enabled). It goes in as max does: with the key max made for the boot (`ssh.key` in the VM's directory) to the guest's sshd on the VM's vsock socket, through systemd's `systemd-ssh-proxy vsock-mux/…`. It is for root, who reads max's files. Nothing in the guest changed for it, so it works on a VM whatever booted it. max doesn't know of the session: a VM that isn't kept on is still stopped once max has had no use for it for its idle time.
  - **A running VM is a machine of the host's**: the unit's `ExecStartPost`, run as root, registers it with systemd-machined as `maxx-7`, class `vm`, service `maxx`, the leader cloud-hypervisor (`RegisterMachine` on the bus; a name a boot that just ended left is dropped first). `machinectl list` shows it, `machinectl status maxx-7` its unit and processes, and `machinectl terminate maxx-7` stops the unit; machined forgets it when cloud-hypervisor ends. A registration that fails is only logged. As the unit changed, a VM is registered from its next boot on.
  - **`machinectl login` and `shell` can't take a VM**, in systemd 260 as tank runs it: machined opens a terminal only in a container or on the host (`machine_openpt` answers a VM with "not supported"). Nor does `ssh machine/maxx-7`: for a VM it wants an `AF_VSOCK` CID the host's kernel reaches, and cloud-hypervisor's vsock is a multiplexer on a UNIX socket (the `vsock-mux/` address). So the way in is `maxx-ssh`.
  - **Tests**: the nested test finds the machine with its unit and leader, runs a command with `maxx-ssh`, finds the new leader after the VM is killed and booted again, and neither once the VM is stopped.
- **Volumes** are owned by `maxx` and are removed only on explicit deletion.
- **Installing and searching packages:** `maxx` builds through the nix daemon and places gc roots in `/var/lib/maxx/gcroots/<conversation id>/`; the guest sees them through the read-only store share. Root is not required.
- **Resource limits:** memory and vCPUs are capped by hypervisor parameters (8 vCPUs and 16 GiB per VM on tank). Individual VMs have no cgroup of their own, and there is no limit on all VMs combined: `maxx.slice` sets no memory limit, because such a limit would also constrain maxx itself and kill processes once reached. Memory is allocated only when used, and pages freed by the guest are returned to the host through the balloon's free page reporting; the guest's page cache does not count as free and is kept until the VM's idle shutdown (decided 2026-10-30 by the owner's choice: a VM normally uses 1–2 GiB, and memory becomes tight only when several groups run large builds at the same time, at which point the page cache can be dropped inside the guest once it is idle). cgroup delegation can be added later if needed.
- **Idle VMs drop their caches** (decided 2026-11-03): every 10 minutes, if nothing of Max's runs in it and none has begun or ended in the last 10 (`maxx units idle 600`), the guest runs `sync`, `drop_caches=3` and `compact_memory` (`max-trim.timer` in `nix/jobs.nix`). So a guest's caches go 10 to 20 minutes after the last of its units, and again every 10 for as long as it stays unused. Until 2026-11-12 the host had it do so over SSH once a VM had gone unused for 10 minutes; for a day after that the timer asked only that nothing ran at that moment, which could fall between two calls of a turn and have the second read from disk what the first had written, and the owner had the wait back on 2026-11-13. `maxx units idle` reads the time from `/run/max/jobs`: a unit's start makes its directory there, its end writes in it, and the directory goes once the end is told. The page cache is released, as are the cached dentries and inodes (virtiofsd closes the corresponding descriptors in turn), and the large blocks of free pages produced by compaction are returned to the host via free page reporting: for shared memory (`shared=on`, memfd), cloud-hypervisor v52 first punches holes with `fallocate` and then applies `MADV_DONTNEED` (confirmed by reading the source). VMs kept running are cleaned as well. Balloon resizing, virtio-mem memory hot-plug and vCPU hot-plug are not used: idle vCPUs cost the host nothing, memory is allocated only when used, and shrinking a VM's limit merely forces the guest to drop its cache, so dropping the cache directly is simpler and avoids opening an API socket for cloud-hypervisor. Data from tank on that day: over one week, at most 7 VMs ran at the same time, and usually 1–4; the 7 running VMs used between 0.8 and 5.7 GiB each, and virtiofsd used a further 4.3 GiB, of which the store virtiofsd of one private chat held 1.67 million open descriptors (someone had scanned the store again); CPU and memory pressure on the host were both close to 0. The VM specification (8 vCPUs, 16 GiB, 64 GiB disk), the two-hour idle shutdown and the 32 slots therefore remain unchanged.
- **File descriptors of the store share:** for every store file the guest has looked up, the store's virtiofsd keeps an O_PATH descriptor open until the guest's kernel forgets that file; if the guest has enough memory, it never forgets. On 2026-10-30, a background agent looking for glibc's ld-linux ran `find /nix/store` and scanned the host's entire store (6.41 million files at the time); virtiofsd exhausted the 524288 descriptors allowed to `maxx.service`, after which every store file newly looked up in that VM failed with `Too many open files in system` until the VM restarted. Therefore:
  - `LimitNOFILE` is raised to 8388608, and virtiofsd raises its own soft limit to the same value, which is enough for a scan of the entire store. The cost is host kernel memory, about 1.4 KB per open file (1048 B for a bcachefs inode, plus 192 B each for the dentry and the file); a scan of the whole store costs about 9 GiB, which is returned once the guest forgets the files or the VM shuts down.
  - The prompts of Max and of background agents state that, to find a file in a package, the path should be obtained with `nix build --no-link --print-out-paths nixpkgs#<package>`, rather than by running find or ls, or using wildcards, under `/nix/store`.
  - virtiofsd's `--inode-file-handles` (which stores handles instead of keeping descriptors open) is not used: `open_by_handle_at` requires `CAP_DAC_READ_SEARCH` in the initial user namespace, and that capability allows any file on the host's file systems to be opened by handle.
- **Security:** a VM escape yields `maxx`, which is better than the Haskell version's root, but `maxx` can read the database and the secrets. cloud-hypervisor runs with seccomp and Landlock enabled, and virtiofsd enters its own namespaces; see the verification below.
- **Differences from the Haskell version:** VMs no longer have their own network namespaces. The Haskell version used a netns plus NAT, and the guest was always `10.0.2.2`; the guest image's network configuration has to change accordingly.
- **Verified on tank** (2026-10-29, borrowing the Haskell version's guest, running as `maxx` under the hardening of `maxx.service`):
  - cloud-hypervisor 52 uses the pre-created multi-queue taps without needing `CAP_NET_ADMIN`. It merely notes that the tap already exists and does not change its address.
  - When run as an ordinary user, virtiofsd 1.13 enters new user, mount, pid and net namespaces by itself, changes its root directory to the shared directory, and holds no capabilities. In `/work`, creating, deleting and renaming files, symbolic and hard links, chmod, flock, git and writing a 300 MB file all work. The guest's root is mapped to `maxx` and every other uid is squashed to `maxx`, so chown reports no error but has no effect; mknod fails, as in the Haskell version. `meta` and `chat` need the same mapping; otherwise `authorized_keys` in the guest is not owned by root and sshd refuses it.
  - The hardening of `maxx.service` has to be relaxed in four places, and nothing else changes:
    - Remove `ProtectKernelTunables`, `ProtectKernelLogs` and `ProtectHostname`. They overlay read-only mounts on `/proc`, and the kernel then refuses to let virtiofsd mount another proc in its own user namespace. For a service without capabilities, these three options did not block much in any case.
    - `RestrictNamespaces` allows user, mnt, pid and net, which virtiofsd's sandbox needs.
    - `SystemCallFilter` adds `@mount`.
    - `PrivateDevices` stays; `/dev/kvm` and `/dev/net/tun` are brought in with `BindPaths` and permitted with `DeviceAllow`.

    `RestrictSUIDSGID` incidentally prevents the guest from setting the setuid bit in `/work`.
  - cloud-hypervisor's Landlock can be enabled, but two rules must be added: `/sys/devices/virtual/net` read-only (to read the tap's flags) and the VM directory read-write (to create the vsock socket). Once Landlock is enabled, cloud-hypervisor has no capabilities, runs with `NoNewPrivs`, and has a seccomp filter.
  - It takes about 3.8 seconds from starting the process to a working SSH connection. SSH over hybrid vsock first sends `CONNECT 22\n`, after which systemd's `systemd-ssh-proxy vsock-mux/<socket>` can connect; russh simply does the same.
  - In the guest, `systemd-run --pipe --wait` brings back the output and the exit code. It writes escape sequences that set the terminal title into the output, so `SYSTEMD_ADJUST_TERMINAL_TITLE=0` must be set.
  - tank's CPU has nested KVM enabled, so the guest can also be started inside the module's NixOS tests. The flake's `nestedChecks.x86_64-linux.vm` does exactly this: inside the test machine, the module sets up the taps, nft and the hardened `maxx.service`, and the equally hardened `maxx-vm-check` then starts a VM and runs `uname -a` through the same path that `shell` uses. It passed on tank on 2026-10-29, with the VM inside the test machine ready in 10 seconds. CI runners are themselves VMs and cannot give the test machine KVM, so this test is not part of `checks` and has to be run manually on tank.
  - **aarch64 can be deployed too** (requested by the owner on 2026-11-05): the flake's `guest` and `nestedChecks` also exist for aarch64-linux. On x86_64, cloud-hypervisor boots the ELF `vmlinux` directly; on aarch64 it boots `Image` and the serial port is a PL011, so the kernel and the console are chosen per architecture (`ttyS0`, `ttyAMA0`), as in microvm.nix's own runner; the x86_64 guest has not changed by a single byte. aarch64 has no early output comparable to `earlyprintk`, so with `quiet`, `serial.log` is normally empty. Verification: in a copy of the Mac's Linux builder (Virtualization.framework, with nested virtualisation enabled), `max vm-check` was run as an ordinary user; the guest came up, `uname -m` reported aarch64, and programs could call tools through MCP. Chromium and ffmpeg from the same guest also ran normally when run directly in the builder. However, the guest there sits beneath two layers of virtualisation and is more than ten times slower than on tank (50 seconds to boot, two minutes of CPU time to start Chromium), and all of the browser checks timed out, so the browser has not yet been fully verified in an aarch64 VM. The aarch64 `nestedChecks` need an aarch64 machine with nested KVM, which the Mac is not (see the next item).
  - **The nested test on the Mac** (tried on 2026-11-12 and 13 at the owner's request, as the link to tank is often unstable): it runs, but too slowly to pass, so the flake has no Mac variant. The Linux builder cannot host it: the virtual EL2 that Apple provides lacks VHE, so the builder's KVM can only run in nVHE mode, the kernel rejects `kvm-arm.mode=nested`, and the test machine there has no KVM. What does work is the test driver on macOS with the aarch64-linux test machine under QEMU 11.1 or later (the deploy's pin has 10.2), which gives the machine EL2 through HVF on an M3 or later. That took three things:
    - Apple's vGIC. nixpkgs starts a test machine on macOS with `gic-version=2`; QEMU then emulates the GIC and the EL2 physical timer itself, the machine's clock jumps (from 1 s to 735 s) and it hangs in the initrd. Adding `-machine gic-version=3,virtualization=on,kernel-irqchip=on` to `virtualisation.qemu.options` (QEMU merges it into nixpkgs' `-machine`, the later key winning) uses Apple's GICv3 instead: the machine is up in about 13 seconds, with KVM.
    - Linux 6.12 in the test machine. Under Apple's EL2, KVM in 6.18 and 7.2 cannot run a VM: the VM gets no interrupts and stops early in its boot, whatever kernel it boots. KVM in 6.12 runs it. This was not bisected or reported upstream.
    - The test machine's configuration has to take its own `pkgs`: on macOS the test file's are the host's, and a darwin `postgresql` ended up in the Linux machine. nixpkgs' `qemu.forceAccel` cannot be used: its check on macOS runs `sysctl`, which is not on the build's PATH, so it never finds HVF.

    With these, the group's VM booted in 62 seconds (10 on tank), and `shell`, `run_code` over MCP, background commands and units worked; but every browser call failed, Playwright's `connectOverCDP` timing out after 30 seconds, and `vm-check` took 19 minutes. Eight cores and 8 GiB for the test machine were no faster. A benchmark one level down, a busybox guest under cloud-hypervisor, shows why: a loop that only computes runs as fast as in the test machine, and an idle guest uses about 1% of a core, but every exit (I/O, virtiofs, stage-2 faults) goes through Apple's EL2 and the test machine's KVM, so a systemd boot or a browser's start is 6 to 10 times slower. Passing would take longer time limits throughout max and the test, for one slow host. The nested test stays on bare metal, where the test machine is the only VM: tank, or another x86_64 Linux machine.

## The operations network

Implemented 2026-11-05 (requested by the owner), copying the Haskell version's approach (`nix/operations.nix` at `haskell-base`), except that the VMs now use cloud-hypervisor taps.

- **Approach:** on tank, a network namespace `maxx-ops` runs a dedicated tailscaled, which is the node `maxops` in the tailnet (Headscale user `max@imdomestic.com`). The VMs of the groups listed in the configuration (`vm.operations.conversations`, given as conversation ids so that group numbers are not written in the public repository) use a separate set of taps (`maxx-ops0…`, 10.236.0.0/24), and the host routes all traffic from these taps into the namespace by source address (`ip rule from 10.236.0.0/24 lookup 236`). Inside the namespace, traffic to the tailnet and the subnets it advertises goes through tailscale0, while everything else returns to the host through the uplink and goes out to the internet; both paths are masqueraded as the namespace's own address.
- **networkd must keep this rule** (2026-11-07): each time systemd-networkd configures an interface it manages, it deletes any ip rule not written in that interface's `.network` file (`ManageForeignRoutingPolicyRules`, enabled by default). When tank restarted on 2026-11-06, networkd configured `ens6` five seconds after `maxx-ops-network` had added this rule, and deleted it; packets from the operations VMs then followed the host's main routing table out through br-lan and were rejected by the `oifname != maxx-uplink` rule (ICMP admin-prohibited, seen in the VM as "Packet filtered"), so the VMs could not even reach the internet. This went unnoticed until 2026-11-07, when someone in the group asked Max for a report. Now, a host that uses networkd must write this rule into the `.network` file of an interface networkd manages (on tank it is written in nix-config's `hosts/tank/maxx.nix`, attached to `30-br-lan`), or else the module's assertion refuses to build; `maxx-ops-network` first deletes every identical rule and then adds it back with `proto static`, making it the same rule that networkd adds: networkd compares rules including their protocol, and deletes those whose protocol differs. The owner wants to keep `ManageForeignRoutingPolicyRules`, so it has not been turned off. The nested test machine has also switched to networkd and checks that the rule survives `networkctl reconfigure` and a restart of `maxx-ops-network`.
- **Login without keys:** the fleet's machines run Tailscale SSH, and Headscale's SSH policy admits `group:imdomestic` (which includes `max@`) by tailnet identity. Each machine has a `max` user with passwordless sudo (nix-config's `system/modules/max-operator.nix`). The VM holds no key and cannot reach tailscaled's socket or node state.
- **The guest:** the VM's kernel command line gains `max.domain=<tailnet domain>`, and `100.100.100.100` is placed first among the DNS servers (MagicDNS answers only tailnet names and returns SERVFAIL for everything else, whereupon glibc asks the next server). From these, `max-guest` writes `/run/max/ssh_config`: short names are completed with the domain, and it sets `User max`, `BatchMode` and `StrictHostKeyChecking accept-new`; known_hosts lives in `/work/.ssh` (root's home directory is /work). The guest's ssh_config always `Include`s this file; other VMs do not have it, and ssh ignores the missing file.
- **What the host enforces:** traffic from the operations taps can only enter the namespace (anything with `oifname != maxx-uplink` is rejected), so even when the namespace is not up it never falls through to the host's own tailnet node; traffic leaving the namespace can only reach the internet, and cannot reach the LAN, other VMs, the host's tailnet or the host's services. The namespace does not accept new connections from the VMs. tank itself cannot be reached over ssh: its tailnet address is a local address on the host, so the VM's packets are delivered locally into the host's input chain and rejected; in any case, the machine that runs maxx and all the VMs should not let a group obtain root.
- **ssh in the guest:** `programs.ssh.systemd-ssh-proxy` must be disabled. Its Include is a file in the store, which on virtiofs does not appear to be owned by root, so ssh rejects the entire configuration ("Bad owner or permissions") and cannot connect anywhere. The Haskell version disabled it as well. Tested live on tank with `vm-check --operations` after the 2026-11-05 deployment: `ssh h610 hostname` and `ssh h610 sudo -n whoami` (root) both work, and the host key was recorded in `/work/.ssh/known_hosts`.
- **Prompt:** the system prompt of these groups ends with an additional "operations network" section covering how to ssh, passwordless sudo, explaining clearly before changing anything, and placing long tasks in a remote systemd-run or tmux.
- **Permissions:** as in the Haskell version, anyone in the group can have Max act on the fleet, which amounts to root. It should be enabled only for trusted groups.
- **Slots:** operations groups use only the operations taps (4 by default), and ordinary groups use only the ordinary ones; when the slots are full, each class evicts its own VMs by idle time. When the list changes, a running VM switches taps only at its next boot.
- **State:** the node identity is that of the Haskell version's `maxops`, copied on 2026-11-05 from tank's `/var/lib/max/tailscale` to `/var/lib/maxx-ops-tailscale`, so no new preauthkey was needed; `vm.operations.authKeyFile` is kept for logging in from scratch.
- **Checks:** `max vm-check --operations --command "ssh h610 hostname"` starts a VM on the last tap of the operations network and runs the command. The nested NixOS test uses a fake "tailnet" (a veth in `maxx-ops` connected to 100.64.0.2 in another namespace): the operations VM can ping it, while the ordinary VM cannot and has no ssh_config either.
- Code: `config::Operations`, `Free` in `vm.rs`, the command line in `vm/machine.rs`, `max-guest` in `nix/guest.nix`, and `vm.operations` in `nix/module.nix`.

## A VM's forwarder

Done 2026-11-14 (the owner: do this and the rows, and leave the context). Until then `/llm` and `/api` were routes of max's service to each VM, so every deploy cut an agent's model call in the middle (pi tries again, which is why this was bearable) and any `git push` or API call in flight.

- **A unit for each VM**, `<name>-forward@<conversation>`, which runs `max forward --dir <the VM's directory>`. It is bound to the VM's unit, which wants it: systemd starts it with the VM and stops it with it, and max does neither. A deploy that changes it leaves those that run, as it leaves the VMs (`restartIfChanged = false`); a VM has the new one when it next boots.
- **The front door on the host.** The forwarder listens where cloud-hypervisor connects when the guest connects to the host's port, `notify.vsock_7777` in the VM's directory, which was max's socket. It answers `/llm` and `/api` itself, with the code that answered them in max (`service/forward.rs`, `forward/api.rs`), and passes everything else on to max, which listens at `max.sock` beside it: the tools, `/events`, `/units`. A guest is told nothing new, and nothing in a group's `/work` that names `127.0.0.1:7777`, a git remote among them, had to change.
- **While max is away** the forwarder can't connect, and answers as max does of a call that comes while it stops, 503 with `max-away`: nothing was passed on, and the guest's client asks again. A request max had and didn't answer is a failed call, `closed`, which may have acted. A request the guest drops is dropped at max, which cancels the call, as closing the connection always did. Each request is a connection of its own to max: one kept from before a restart would fail a call max never saw, with no way to tell.
- **Its configuration is a link**, `forward.config` in the VM's directory, to the file max was started with. max makes it when it boots the VM and makes it again each time it attaches, and the forwarder looks every two seconds: a link made again is read again, the keys its file names too, even when it names the same file. So a deploy's new models and keys reach the forwarders that run when the new max is back, with no restart of theirs. A new configuration is served by a new server on the same socket, and the old one ends when its calls do. The forwarder reads only its own of the file, `[database]`, `[llm]`, `[api]` and `[log]` (`config::Forwarded`), so what a newer max has elsewhere doesn't stop an older forwarder; a file whose `[llm]` or `[api]` it can't read is left, and it goes on with the last. Nothing with a secret is written into the VM's directory, which cloud-hypervisor may read: the file names the secrets' files, and the forwarder reads them.
- **An API's hour is still every chat's together** (tank's Bungie key has 1000 calls an hour): the forwarders count an API's calls in one file under `<vm.dir>/api/`, locked while it is read and written, a line a call of the last hour. A count that can't be kept there is kept in the process, and logged.
- **max keeps no key of an API's**, only their lines in the system prompt. It still reads the secrets and the models' keys once as it starts, and lets them go, so that a missing one stops max at a deploy, not a forwarder when a VM boots. A model call's usage is recorded by the forwarder, as max recorded it.
- **vm-check** names its VM's forwarder a configuration of its own: the one it was given, with a provider of its own for the agents, which counts what it is asked.
- **The contract is 6.** A guest says nothing new, but a VM an older max booted has no forwarder, and nothing listens where its guest calls: every VM boots again at the deploy, into this.
- **Tests:** the forwarder's own (`forwarder/tests.rs`): its routes with max there and away, a stream passed on as one, a call dropped by either end, a new configuration read, a newer one's unknown parts left, an unreadable one refused. The nested test asks the agents' model for an answer that takes eight seconds, stops max in the middle, and has the answer whole; the forwarder answers `GET /llm` with max gone, and reads the new configuration after a deploy without a restart.
- **Not done:** a forwarder's code is as old as its VM's boot. Only what it reads follows a deploy.
