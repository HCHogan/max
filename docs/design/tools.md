# Tools and codemode

## Tools and codemode

Decided 2026-10-27.

### Pure codemode

- **The model has only two tools: `run_code` and `shell`.** The tools array is fixed, so the request prefix is never invalidated by a change in tools; what must be preserved is that the set is "fixed", not that there is "only one" tool. The parameters of `run_code` are `{code, args?, timeout_ms?}`: `code` is the body of an async function, and the value it `return`s is the result; `timeout_ms` behaves as it does for `shell`. One round may contain several `run_code` calls, each running independently.
- **Calling Max's tools from a program:** `tools.<name>(args)` returns a Promise, so `Promise.all` provides concurrency. The shape of the Haskell version's SDK is kept: `max.raw` obtains the full success-or-failure result, `max.cancel` and `max.race` cancel calls, and `tools.agent()` dispatched a background agent (implemented 2026-10-30; a shell command from 2026-11-12, and `tools.agent_start` since 2026-11-14; see [Background agents](jobs.md#background-agents)). Implemented (2026-10-29): `tools.x()` throws `ToolError` on failure; `max.raw` does not throw, and returns `{ok: true, value}` or `{ok: false, error: {code, message}}`; `max.cancel` aborts that request, and `max.race` takes whichever call finishes first and cancels the rest; reading a field without awaiting raises an error immediately, with a hint to await first.
- **`shell`** (decided 2026-10-28): runs terminal commands without a detour through JS. With only `run_code`, every command would require writing `child_process` code; a non-zero exit throws an exception outright and stderr is lost; the command is nested in a JS string that is in turn nested in JSON, which adds a layer of escaping, and any `${VAR}` inside a template string is consumed by JS first. Mainstream models are trained most heavily on shell tools, and a shape close to what they know works best.
  - The parameters are `{command, workdir?, timeout_ms?}`, close to Codex's shell tool. The command is executed in the group VM with `bash -lc`; the default working directory is `/work`.
  - The result is the exit code plus the combined output; overly long output keeps its head and tail, and the full text is written to a file in the VM. The wall-clock limit is the same as for `run_code`.
  - Originally it could not call Max's tools and did not open an MCP session, and handing over an image required a further `run_code` call. Since 2026-11-02 it opens a session just as `run_code` does, and commands call tools with `maxx`; see the next item.
  - It introduces nothing new in terms of security: `run_code` could already call `execSync`, and everything in the VM already runs as root.
- **`maxx`** (implemented 2026-11-02, proposed by the owner as "language-independent codemode"): a command in the VM through which `shell` commands, and programs written in any language, call Max's tools.
  - **Tools have a single source:** each tool is still written in only one place, on the host (`service::tool::TOOLS`; see "Tool contract" below). The runner's `tools.<name>` and `maxx` are both merely generic clients of max's service that call tools by name; neither contains code specific to any tool, and a new tool automatically becomes available in both.
  - **One client:** the calling code was extracted from `runner.js` into `nix/client.js`, which the runner and `maxx` (`nix/maxx.js`, written for Node) share. The reverse arrangement, in which the SDK wraps `maxx`, was rejected: every `tools.x` would then start a process, a `Promise.all` over twenty queries would mean twenty processes, and errors and images would have to be relayed through exit codes and stdout. The cost is that every `maxx` invocation starts Node once, which takes a few tens of milliseconds; a loop of a hundred calls should use `run_code`.
  - **Usage:** `maxx tool-name --param value` or `--param=value`; a bare `--param` means true and `--no-param` means false. Alternatively, a single JSON object may be given, with `-` reading it from standard input. Words without a parameter name fill the required parameters in order, then the remaining ones. Arguments are converted to the types in the schema that `GET /tools` lists; repeating an array parameter yields several items. `maxx` on its own lists the tools, and `maxx tool-name --help` shows a tool's parameters and description. The guest's own tools are not in that list, so `maxx` reads them from `local.json`, `maxx show path` (`tools.show`) among them; see "One command" below. `maxx file handle` is one of the host's tools since 2026-11-12. `maxx events` is not a call but a stream of the group's messages; see step four of [Resident programs](jobs.md#resident-programs).
  - **Results:** on success, JSON is printed to standard output; when a tool fails, "tool: reason (code)" is written to standard error and the exit code is 1; a malformed command line exits with code 2.
  - **Sessions:** a foreground `shell` opens an MCP session just as `run_code` does, and the token is placed in the command's environment variable `MAXX_TOKEN` via `systemd-run --setenv`. The runner likewise puts its own token in `process.env`, so child processes started by the program can use `maxx`. Tools called from a command are therefore also counted in the "Max tools called" line, and images from `maxx show` follow the `shell` result. Background commands outlive the turn and have no token; a command that outlives its run with one, as a moved command does, calls as a program from then on (2026-11-11). All of this went on 2026-11-12: no call has a session or a token, the line "Max tools called" is gone, and what `maxx show` leaves is a line in the call's directory (see [Multimodal results](#multimodal-results)).
  - **Without a token** (resident programs and background commands, implemented 2026-11-02): the call belongs to the group whose VM's socket it came in on, and to no run. Such a caller has every tool (a subset at first, every one since 2026-11-05), including `say` and `wake`, but not `show` or `video`, as nobody is there to see them. See step three of [Resident programs](jobs.md#resident-programs). Since 2026-11-12 this is every call: a turn's program and command call the same way.
  - **The same tools in both** (2026-11-11, the owner): the runner's `tools` has every tool, as a turn's `maxx` does; until then it had only those the prompt declares, so `tools.say` was missing while `max.raw("say", …)` and `maxx say` both worked. Leaving a tool off one client of the same service kept nothing out. Which tools a caller has is decided only by `Caller::route` on the host; what the prompt declares is a separate choice. `Caller::route` went on 2026-11-12: every caller has every tool.
  - **One command** (2026-11-14, the owner: everything of Max's in a guest goes by `maxx`, the host calls it as anything in the VM does, and a program has all of it too). Until then the guest had `max-jobs`, `max-agent`, `max-units` and `max-wake` beside `maxx`. When the agents became units of the guest's (2026-11-12), starting one stopped being a tool of the host's, so it left the host's list, and with it both `maxx` and `tools`: what the guest does itself had commands of its own, and no form in a program.
    - **The guest's own tools are declared once too**, in `nix/local.json`: a name, the words of its command line, what runs it (`run`: one of the guest's scripts, or Node), whether the system prompt declares it (`turn`), a line for `maxx`'s list, the guide for the prompt, and both schemas. `maxx` reads its options from there as it reads the host's from `GET /tools`, the runner makes `tools.<name>` from it, and the host reads the same file as it is built, for the TypeScript in the system prompt (`service::tool::LOCAL`): the prompt's declarations, the command line and the program's form come from one file. A test holds that no name is both the host's and the guest's.
    - **The commands:** `agent start`, `agent steer`, `agent models` and `agent ask`; `units list`, `units apply`, `units start`, `units run` and `units stop-all`; `show`, `video` and `events`. What were jobs and what were units are one group (the owner: both are units): `units list` has what was started, each a `call`, a `job` or an `agent`, and what `/work/.max/systemd` keeps, each a `unit` with its state as systemd has it; `units stop-all` stops the first kind only, as `/kill` always did. A tool of the guest's goes by its words and by nothing else: `maxx agent start`, not `agent-start` or `agent_start` (the owner). In a program it is `tools.agent_start`.
    - **Declared in the prompt:** `show`, `video`, `agent_start`, `agent_steer`, `agent_models`, `units_list` and `units_apply`. The rest can be called and aren't declared, as `say` and `wake` aren't: `agent_ask` is an agent's, `events` a program's, and `units_start`, `units_run` and `units_stop_all` are what `shell`, `run_code` and `/kill` are made of.
    - **How one runs:** `bin/maxx` is a shell script (`nix/maxx.nix`). Given a guest tool's words and a JSON object alone, it runs the tool's script with them, `max-jobs.sh`, `max-agent.sh` or `max-units.sh`, and Node never starts. That is how the host calls: `maxx units run '{…}'` for every `shell` and `run_code`, and `units start`, `units list` and `units stop-all`. The units' own hooks are there too and are no tools: `maxx units ended`, `notify` and `idle`, and `units agent` for an agent's unit. Anything else goes to Node (`maxx.js`), which reads the options against the schema and calls `maxx` back with the JSON; a program's `tools.<name>` does the same (`tools.js`), so a guest tool runs one way whoever calls. Which words go to which script is generated from `local.json` when the package is built. A script answers with one JSON object on stdout; a failure is its reason on stderr and status 1, and a wrong command line status 2, which a program sees as `failed` and `bad_arguments`.
    - **A value of `-` is standard input**, for an argument that is text: `maxx agent start --title … --task - <<'EOF'`, which is how the prompt has Max start an agent. A bare `-` is still the whole JSON object.
    - **Answers are JSON**, as the host's tools' are. `units apply` says each unit's state, the files it skipped and why, and what it removed, where `max-units` printed lines and failed when a unit had; `agent start` gives `{name, said}`; `units start` gives `{unit, limit, said}`, and `said` is what `shell` with `background` tells the model: the sentence is the guest's, the same whoever starts one.
    - **`max.image` and `max.video` are `tools.show` and `tools.video`**, the names `maxx show` and `maxx video` had: `tools.show({path})`, or a picture's bytes in place of the arguments, `tools.show(await page.screenshot())`. `max` keeps what isn't a tool: `raw`, `cancel` and `race`, and the browser's `page`, `browser` and `snapshot`.
    - **`tools.events({after})`** is what `maxx events` prints, for a program in JS: an async iterator of the rows (the owner: so that Max can write that logic in JS). A program of Max's own, which isn't run_code's, has the same `tools` with `require("/run/max/tools.js")`, which the guest links beside the runner: without it only a run_code program, which ends within minutes, could follow the chat in JS.
    - **A call's caller is a pipe or a socket:** `units run` takes the end of its standard input for its caller gone only when that input is one, as max's channel is and a program's child's. Given `/dev/null`, as a command in a unit is, nobody holds it, and the call runs to its end; until then such a call was stopped at once.
    - **Old names:** none is kept (the owner: what uses them is moved by hand). The contract is 5 with this, so every VM boots again at the deploy.
    - **Arguments are read strictly** (2026-11-14, after a review of the command line, which found the groups and the names sound and the reading of arguments loose; no change to the contract, as max sends only what the tools take):
      - *A word that begins with a brace* is the arguments as JSON when it is a JSON object, or begins as a program writes one, `{"`; any other is a text. Until then every such word was taken for JSON, so `maxx say '{笑}'` failed, and `maxx units start '{ make; } 2>&1'`, a command in braces, went to the script as broken JSON. `bin/maxx` takes `{}` and `{"…` for a guest tool's JSON and hands the rest to Node.
      - *After `--` every word is by position*, whatever it begins with, and `-h` asks for help in the first place only: `maxx say -- '--x'` and `maxx say --text -h` say what they were given.
      - *A guest tool refuses a field it doesn't take*, as the host's tools do, and one that takes no arguments refuses any: `tools.units_start({command, timeout_ms})` ran for the 6 hours nobody asked for, in silence.
      - *A name written another way is told its words:* `maxx agent-start`, `agent_start` and `maxx units stop_all` each say how it is written, where they listed every tool. Only the words run it, as before.
      - *`--help` says how a tool is used and what it returns:* the guide the system prompt has, which the host's list carries now (`guide`), and the result's shape from its schema. A background agent is told of no tool in its prompt, so this is all it has.
      - *`maxx events` reads its arguments as a call does*, so `maxx events 123` and `maxx events '{"after": 123}'` work as they do for any tool.
      - *A host tool given its arguments as one JSON object is called at once:* the list isn't asked for first, since no schema is needed to read them, and the host says itself that it has no such tool. Measured in a guest that day, one request to the host costs about 95 ms, Node's start 65 ms, and `maxx history --limit 1` 307 ms with its two requests.
      - *One name is one unit's:* `units start` and `units run` refuse a `unit` that is there already. A second start wrote over what the first was known by, failed in systemd, and removed it, so the first's end was told to nobody.
      - *`units list` is one `systemctl` and one `jq`* for all it lists, where it ran one of each for every unit (0.43 s for 16 of them); and a unit that ends as it is read is left out, where the list failed, and max took a failed list for nothing running.
    - **Tests:** `nix/tests/jobs.nix` asks as max does, with JSON, and as Max does, with options, and has a program call `tools.units_list`; the Rust tests run `maxx.js`, `runner.js` and `tools.js` with Node against a stand-in for `bin/maxx`.
- **Tool descriptions:** the system prompt contains TypeScript declarations of Max's tools, including return types; this content is fixed.
- **A skill is only documentation.** `use_skill` is an ordinary Max tool that returns the manual and the declarations of the related tools, which, like any other result, are only appended to the end of the context. Which tools may be called is determined by the group and the conversation; it does not change within a turn, and it does not change when a skill is loaded. The core therefore has no "active tool set", and neither Responses' `tool_search` nor meta-tools for Chat Completions are needed.
- **Call format:** the most common form, a function tool with JSON arguments, is used. Whether the code arrives as original text or escaped inside a JSON string depends on the model's own tool-call format: Claude's string parameters and the XML parameters of Qwen 3.5/3.6 carry the original text; GPT and Gemini require escaping, and Gemini occasionally adds an extra layer of escaping (gemini-cli contains code written specifically to correct this). aider measured this in 2024: once code was wrapped in JSON, the pass rate of every model tested dropped, by varying amounts. This is not addressed for now; see [Open items](#open-items).
- **Cost:** every tool depends on the VM. If the VM cannot start, no tools are available, although the model can still answer in plain text; `/status` must show the VM's state. Frontier models write JS without difficulty; local models such as qwen3.8-27b are to be evaluated in v1.

### Running in the group VM

Programs run on Node inside the group VM rather than in an in-process JS engine (the Haskell version used QuickJS inside wasmtime). The benefits are:

- `/work` is shared with the background pi, so handing over a task only requires leaving files behind; images and files from the group are copied into `/work/chat` with `max.file()` and read from there (see [Reading files](media.md#reading-files)).
- The browser is driven directly with Playwright (see [The browser](#the-browser)).
- Max does not have to maintain a JS engine, a single-step protocol or an ABI.

The approach:

- **A new process for each run:** the host executes `node /run/max/runner.js` in the group VM over SSH on vsock. The runner and the SDK are built into the guest image and are read-only. stdin carries the program, the arguments and the names of Max's tools (and until 2026-11-12 the session's token); stdout carries only the return value (a string as is, anything else converted to JSON), while `console` output and anything the program itself writes to stdout are redirected to stderr and brought back as logs. Exit code 0 means a normal return, and 1 means an exception was thrown, reported with the program's own line number. Like `shell`, each run is a transient unit started through `bash -lc`, so child processes of the program have a login environment. No resident process is used, so that no state is shared between runs. `shell` likewise uses one SSH channel per run and invokes `bash -lc` directly, without going through the runner.
- **Startup:** the VM is started on demand and can execute commands after about 4.5 seconds (verified in testing with the Haskell version); it shuts down after two hours of idleness. VM startup begins as soon as a `run_code` or `shell` call appears in the model's output stream, overlapping with the time the model spends writing the code; turns that use no tools do not start the VM.
- **Limits:** the VM's CPU and memory limits and its network policy; a wall-clock limit for each run of `run_code` and `shell`, which the guest's systemd keeps (`RuntimeMaxSec=`); a call dropped before its unit ends, as when its turn is killed, has its channel closed, and the guest stops the unit (see "A call" in [Background commands](jobs.md#background-commands)). Determinism is not required, and there is no fuel.
- **Relationship to the core:** to the core, `run_code` and `shell` are each just a single tool call. The Max tool calls made inside a program are not inputs to the core; the result carries a summary of those internal calls to aid troubleshooting.
- **One log line per call** (requested by the owner on 2026-11-03): `a tool call ends`, carrying the conversation, the tool (`run_code`, `shell` or `background`), whether the program used the browser (counted if the code contains `max.page(`, `max.browser(` or `max.snapshot(`), the duration, whether it failed, the token count of the result and the Max tools the program called. The code and output are not logged, because browser programs often contain account names and passwords filled in on someone's behalf. The motivation: in a private chat, gemini-3.8-flash clicked through 126 steps in the Google Cloud console, and the database held only the tokens and duration of each model call, which did not reveal which steps had been wasted. When Max restarts, calls still running when the grace period expires are killed as the connection drops, and the core records them as "cancelled"; see [Restarts](actor.md#restarts).
- **Known risk:** all commands in the VM run as root, and anything there may call every tool of Max's, in a turn or outside one: a process an earlier prompt injection left behind can say things in the chat, mute and recall as Max's programs can. The risk is accepted: a VM is its own group's, and what the tools can do there is what Max can. (Until 2026-11-12 a turn's calls carried a token; such a process could take it or leave it out, so it kept nothing in.)
- **Testing:** the runner depends only on stdio and HTTP, so tests run node on the local machine against max's service on a TCP port, with no VM required.

## The guest's calls

Processes in the VM call the host's tools through max's service, plain HTTP on a socket of the VM's own, with the guest's one client (`nix/client.js`, under `nix/tools.js`): `run_code`'s runner, `maxx`, and a program of Max's own that requires the tools. The guest's own tools ask the host nothing (see "One command" under [Pure codemode](#pure-codemode)). Since 2026-11-14 the socket is the VM's forwarder's, a process that runs for as long as the VM does: it passes the tools' calls on to max, and answers `/llm` and `/api` itself (see [A VM's forwarder](vm.md#a-vms-forwarder)). Until 2026-11-14 the service spoke a slice of MCP, and the section was "The MCP channel"; until 2026-11-12 a background agent's pi was a client too, through its own MCP adapter, and an agent now calls with `maxx`, as any program does.

- **Plain HTTP** (2026-11-14, the owner: MCP is for calling what somebody else wrote, and both ends here are ours). `GET /tools` lists the host's tools with their schemas, and `POST /tools/<name>`, its body the arguments as a JSON object, calls one. The answer is the call's outcome as the client hands it on: `{"ok": true, "value": …}`, or `{"ok": false, "error": {"code", "message"}}` for a call that failed, both with status 200; arguments that are no JSON object are 400 with the same shape. Max stopping is still 503 with `max-away`, and closing the connection still cancels a call. What went: the JSON-RPC envelope and its ids, `ping`, notifications, the `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers, `_meta`, and `structuredContent` beside a copy of itself as text. Why: after rmcp went (2026-11-03) and pi's adapter (2026-11-12) the only client was the guest's own, which came from the same build; the service took one protocol version and refused `initialize`, so no other client could have joined without work; and what a third party would need, the tools declared once with their schemas (see "Tool contract" below), is not in the wire. A page that speaks MCP can be put in front of that table again if another client ever wants one. The names went with it: the module is `service` (`service/http.rs` the routes), the guest's forwarder `max-host`, the runner's input and `maxx` name the host by `url` and `MAXX_URL`. It is part of contract 5.

- **Channel:** with cloud-hypervisor's hybrid vsock, a guest that connects to a port on the host lands on the unix socket `<vsock socket>_<port>` on the host; the Haskell version's readiness notification took this path. At this location Max listens on one port for each VM and serves plain HTTP on axum. Which VM has connected is determined by the socket path. In the guest, `127.0.0.1:7777` is forwarded to this vsock port, and every client is given `http://127.0.0.1:7777`. The host remains unreachable at the IP layer, and the VM remains unreachable from outside. Implemented: the guest side is the socket-activated `max-host`, with one socat per connection to vsock 2:7777; the host listens on `notify.vsock_7777` before the VM starts, with one service per VM that starts and stops with the VM.
- **Protocol** (2026-10-29, until 2026-11-14; see "Plain HTTP" above): protocol version 2026-07-28, stateless, with JSON replies rather than SSE. In this version every request must carry the `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers, and `_meta` must also contain the protocol version and the client capabilities. The runner builds requests itself with fetch and does not install an MCP SDK. Clients of earlier protocol versions were accepted too, from 2026-10-30 until 2026-11-12, when the last of them, pi's MCP adapter, stopped calling: `initialize` is an unknown method now. pi 1.4 uses 2025-11-25 and sends `initialize` first; rmcp, which was in use at the time, by default tried to create a session for it, but the service has no session management and replied with 500; with `legacy_session_mode` turned off, each of its requests is handled independently.
- **No rmcp** (2026-11-03, proposed by the owner, who called it a pure liability): only a small slice is used, stateless and with JSON replies; rmcp's session management, SSE and transport abstractions all go unused, and it instead required configuring `legacy_session_mode` and `NeverSessionManager`, extracting HTTP headers from extensions in `ServerHandler`, and suppressing its logs. It was replaced by a single page of in-house code in `mcp/service.rs` (until 2026-11-14; `service/http.rs` is the plain HTTP that took its place): `POST /mcp` accepts one JSON-RPC message; `initialize` replies with the tools capability and the protocol version (the version the client asks for is granted if it is known, otherwise the latest is given); `ping` replies `{}`; `tools/list` and `tools/call` are unchanged; notifications without an id receive 202; unknown methods receive -32601, non-JSON receives 400 and -32700, and a wrong token received -32600 (until 2026-11-11, when such a call became a program's; see below). GET and DELETE receive 405: there is no session to end and no stream to open. pi 1.4's MCP client is its own implementation (confirmed by reading its bundled code): a notification counts as delivered once it receives a 2xx; the client then sends a GET for a push stream and abandons it on seeing 405; it accepts `application/json` replies; and since we do not send `Mcp-Session-Id`, it does not send DELETE when closing. Headers such as `MCP-Protocol-Version` are not checked. Results follow rmcp's form: alongside `structuredContent`, `content` holds the JSON text of the same value, which is what pi shows the model. rmcp was removed, together with the async-trait, pastey and uuid it brought in. A test walks through pi's handshake over raw HTTP: `initialize`, `notifications/initialized`, GET, `tools/list`, and `tools/call` reading text.
- **Call table** (same day, deduplication): what a program requests by name is an `mcp::Call`: either a Max tool or one of the runner's own three requests, `max.image`, `max.video` and `max.file`. Who may call what (`Caller::route`, the one place since 2026-11-10), how calls are dispatched within a session, and which calls count towards the number of tool calls (only Max's tools) are all decided by this one enum, instead of names being compared separately in `service.rs` and in `mcp.rs`. `max.image` and `max.video` were merged into `mcp/show.rs` and share the steps of reading from `/work`, saving to the content store and recording in the session; the session records `Part` values directly, and the result of `run_code` appends them in the order the program handed them over, instead of keeping one list for images and another for videos. The code that reads an MP4's duration moved to `media/mp4.rs`. `mcp::Call` went on 2026-11-12 with the runner's own requests: `max.file` is the tool `file`, and `max.image` and `max.video` ask the host nothing (`tools/show.rs`).
- **One caller** (2026-11-12, step 4 of [Lifetimes move to systemd](../decisions/2026-11-12-lifetimes-to-systemd.md#lifetimes-move-to-systemd-1)): a call is the VM's. `GET /tools` lists every tool, and a call, `POST /tools/<name>`, goes to the conversation's actor (`Signal::Call`, `Conversation::program_call`), which runs it in `side` within the conversation's call time, with a `Poster` that names no turn; 64 at once for a VM, the rest queued. When the caller closes its connection, the handler stops waiting and the actor drops the call. The host doesn't know what in the VM called: a turn's program, a background command, an agent or a unit of Max's. `service::Context` is the conversation, its services, its `/work` and a `Poster`, or none for `vm-check`, which runs the calls itself.
- **Sessions** (until 2026-11-12): each `run_code` run and each `shell` call opened its own session, which recorded the token, the group and turn it belonged to and the calls in flight. It counted how many times each tool was called and how many calls failed, for the result's line "Max tools called", kept the pictures the program showed, and made what the program said the turn's own. A background agent had one too until step 3. `Sessions`, `Session`, `Grant`, `Caller`, `Route` and `Call` are gone, and so is everything below that speaks of a token.
- **The token names the run, it grants nothing** (2026-11-11, the owner): `Authorization: Bearer <token>` says which session a call belongs to, which only the token can say, since the host sees no more than a connection on the VM's socket. That session decides where the call's pictures go, which result's "Max tools called" line counts it, that what it says is the turn's and not marked as a program's, and, until 2026-11-12, which job's `/llm` and `/job/*` it was. It is not a permission: everything in the VM runs as root and can leave the token out, and a call without one is a resident program's, which has every tool. So on `/mcp` a token that is not open (wrong, from another VM, or its run has ended) counts as none, and the call is a program's. Until then it was refused with -32600, which kept nothing out and refused a command moved to the background (see [Background commands](jobs.md#background-commands)). `/llm` and `/job/*` answered 401 to such a token until 2026-11-12, and a job's session listed and allowed only the tools marked `job`: a limit on what the agent's model was shown, not a wall, since pi's shell could leave the token out. Both went with the agents' sessions.
- **Revocation is synchronous:** removing a session from the in-memory table drops the futures of its in-flight calls along with it, so revocation can be placed in `Drop`. Sessions exist only in memory, so after Max restarts or crashes all old tokens become invalid, and no expiry time is needed.
- **Executor:** every call passes through the same executor, which is responsible for schema validation, the per-call timeout, a concurrency limit of 64, an output size limit, and a limit on the number of calls with side effects (code can send, retract or mute in a loop). Implemented: 60 seconds per call and 64 concurrent calls per VM (per session until 2026-11-12), with the excess queued; arguments are checked against the tool contract (see below). The output limit and the side-effect count will be added once there are tools that produce large output or have side effects; `history` paginates on its own.
- **Results:** tools declare an `outputSchema`, a call's answer is its outcome, `{"ok": true, "value": …}` when it succeeded, and what `tools.x()` receives is the value, as JSON. A failure is `{"ok": false, "error": {"code", "message"}}`. In stateless HTTP, cancellation means disconnecting: when hyper sees that the connection has dropped, it discards that call's future, and `max.cancel` simply aborts the fetch. There is no `notifications/cancelled` any more: until 2026-11-14 it was accepted and ignored, a result was in `structuredContent`, and a failure set `isError`.
- **No retries and no classification by side effect** (decided 2026-10-29, with the owner's agreement): the original plan was to mark each tool as read-only, idempotent or side-effecting, and to include in failure results an outcome (rejected, failed-before-effect, outcome-unknown) and whether a retry is possible, in order to decide on host retries, on which tools background jobs may use, and on whether an interruption counts as "outcome unknown". None of this is needed: the host never retries and leaves that decision to the model; a background job's session lists the tools it may use; and operations that affect the group (sending messages, sending images, retracting) are all entered in the ledger through the conversation actor, so whether they succeeded is visible on the timeline in the next round. Timeouts and cancellations are therefore always reported as "may already have taken effect; check the records before deciding whether to try again". The worst case is calling again immediately after a timeout within the same run and sending one extra image, which is accepted.
- **Tool contract** (implemented 2026-10-30, raised in review: originally the names, descriptions, both schemas and the TypeScript declarations were all hand-written in max-core's `MAX_TOOLS`, while the argument structs and execution functions lived in max; the three copies were each written separately, and some of the constraints in the schemas were not checked at run time): each Max tool is written in only one place, in max, by implementing `service::tool::Tool`, which provides the name, a one-sentence description for the list of tools, the maximum number of calls per run, whether background jobs may use the tool, the argument type, the return type, the usage notes for the system prompt (`guide`) and the execution function. Arguments and return values are ordinary serde types that derive schemars' `JsonSchema`; constraints are written as attributes (`length`, `range`), the descriptions of argument fields are written as `description`, and numbers in the descriptions and in `guide` refer directly to constants in the code. The registry `service::tool::TOOLS` generates three things from these:
  - The `inputSchema` and `outputSchema` that `GET /tools` lists: all sub-schemas are inlined, and titles and integer formats are removed; only the descriptions of the argument fields themselves are kept, and English doc comments on types are left out. When a return value has several shapes (`history`), the schema is an `anyOf`, with `type: object` added at the root, so that a tool's arguments and result are always objects; MCP, which requires the root to be one, was the first reason.
  - Argument checks before the call: string lengths (in characters) and numeric ranges are checked against the schema, with errors such as "history 的 before 要在 0 到 50 之间" ("history's before must be between 0 and 50"); types, required fields and unknown fields are checked when serde reads the arguments. Out-of-range values are reported as errors rather than silently truncated, as they were before.
  - The TypeScript declarations in the system prompt: `/** guide */` followed by a signature converted from the two schemas. Optional fields are written as `x?: T`, and fields that are required but may be null as `x: T | null`.

  serde_json has `preserve_order` enabled, so fields are listed in the order in which they are declared in the type. max-core no longer holds a list of Max's tools, and `prompt::system` receives the finished declaration text. At the switch-over, the generated declarations were byte-for-byte identical to the hand-written ones, so the prompt did not change; the full text of the declarations is covered by an insta snapshot, so a change to any tool's description shows up in the snapshot's diff.

## Multimodal results

The approaches of Codex, pi and Hermes were consulted.

- **Programs hand over images explicitly**, following `image()` in Codex's code mode: `tools.show({path, detail})` and `tools.video({path, start, end})`. `path` is a path in the VM (`/work/…`) or a message handle (`image#123.0`); http addresses are not accepted. Only what is handed over enters the context; operations such as screenshots and downloads only produce files. No separate `view_image` tool is needed.
- **The host fetches the files itself, not through the service:** `/work` is a virtiofs share that the host can read directly, and images referenced by message handles are in the content store. The host checks that the file can be decoded, scales it to the model's limit, and stores it in the content store by hash; the turn record stores only a reference (principle 7). A copy has to be made because files in `/work` may later be changed or deleted.
- **Neutral format:** `ToolOutput { parts: Vec<Part>, error: bool }`, where a `Part` is either `Text` or `Media(MediaRef)`, sharing a single rendering path with the `Media` nodes in messages.
- **Downgrading in the adapter layer** (principle 8):
  - Responses: the parts go into the array of `function_call_output`, as `input_text` plus `input_image`.
  - Chat: the tool message contains only text, with markers such as "图 1 见下" ("image 1, see below"); after all of the round's tool messages comes a single user message holding the images. This also avoids the problem that some providers do not accept tool content in array form.
  - Video: frames are extracted as images. (Changed 2026-11-03: videos are now passed as they are to models that can watch video; see "Video" below.)
- **Budget:**
  - Images are scaled to the limit when they are handed over.
  - At most N images may be handed over per run.
  - When the same image (same hash) is handed over again, only "同上文图 x" ("same as image x above") is written.
  - When an assembled request exceeds the vision token budget, images are replaced, oldest first, with "`[image#… 已省略，需要时再 tools.show]`" ("image omitted; call `tools.show` again if needed"); the turn record is unchanged (principle 6).

  Hermes added this kind of budget after a sub-agent reloaded 5 screenshots 158 times within 15 minutes.

Implemented (2026-10-29, images only at first):

- **SDK:** `await tools.show({path})`, where `path` is a path under `/work`, or `tools.show(buffer)`, a Buffer containing an image in place of the arguments (for example, the return value of `page.screenshot()`); it was `max.image(src)`, with either as `src`, until 2026-11-14. A Buffer is first written to `/work/.max/shown/<unit>/`, the call's own directory there, which `maxx units` clears away an hour later. The call returns `{path}`; a path that isn't a file throws `ToolError`, and whether it decodes, and whether there is room for it, the host says in the result (until 2026-11-12 the call returned `{width, height}` and threw for those too). Message handles have not been implemented; images from the group are first copied out with `tools.file`.
- **How images reach the host** (2026-11-12): nothing is asked of the host. A call's unit has its directory in `MAX_CALL` (`/run/max/jobs/<unit>`), and `tools.show`, `tools.video`, `maxx show` and `maxx video` append a line to `shown` there, `{"kind": "image", "path": "/work/…"}` (`nix/shown.js`). `maxx units run` gives the list back on the call's line, and the host reads the files as it puts the result together (`tools/show.rs`): as with `send_image`, it opens each under `/work` one path component at a time, without following symbolic links, with a cap of 10 MiB; it produces the version for the model in the same way as for downloads (a JPEG with a long edge of 1568, or the original image) and stores it in the content store. The result appends them in order after the text (`Part::Media`, referenced by the content store's sha256), each estimated at 1200 tokens. One that can't be shown (not a picture, too big, one too many, a video for a model that doesn't watch them) is a line of the result, `<path> wasn't shown: <why>`, since the program is over by then; at most 16 entries are looked at. The line carries the first 32 (2026-11-13): max keeps 256 KiB of a call's line, and a program that showed a few thousand pictures used to lose its whole result to a line cut short, which the error then quoted whole; it quotes 300 characters now. What isn't a call has no `MAX_CALL`: there `maxx show` fails with "nobody is there to see it". Until 2026-11-12 the runner sent an MCP call, `max.image`, with the run's token, the host recorded the picture in the run's session, and the program heard at once if it couldn't be shown; without sessions the host can't tell which call a request belongs to, so the path travels with the call instead.
- **Budget:** a single `run_code` can hand over at most 4 images, and the same image (same hash) counts only once. When a request is assembled, all images in tool results are included (changed 2026-11-04, decided by the owner: all images within a turn are kept, and the next turn does not have them anyway). Previously only the latest 8 were included, and older ones were replaced in place with "[这张图省略了，要看再 max.image]" ("this image was omitted; call max.image again to view it"): from the 9th image on, each new image altered an earlier result, and everything from that point onward missed the cache. That text, which says `tools.show` since 2026-11-14, now appears only when the image cannot be read from the content store. Videos are still limited to the latest 10 minutes: a clip can be up to 32 MiB, and keeping them all would make requests too large. "同上文图 x" ("same as image x above") has not been implemented.
- **Downgrading:** Responses writes results that contain images as an array of `input_text` and `input_image`; results without images remain strings. Chat writes "[图 n，见下]" ("[image n, see below]") in the tool message, and after a run of consecutive tool messages comes a single user message with the images placed by number.

Video (implemented 2026-11-03, requested by the owner): the model watches the video directly, with both picture and sound, and no frames are extracted.

- **Why this is possible:** it was tried on tank that day. cliproxy converts the data URL of a `video_url` in Chat into Gemini's `inlineData` (on both the Antigravity and the AI Studio paths), and `gemini-3.8-flash-high` correctly stated the order of three colours in a 6-second test clip, its duration, which section had sound and the pitch of each section. Billing is by duration, at about 87 tokens per second (one frame per second plus audio); size in bytes costs time instead: videos of 14, 28 and 54 MiB were all accepted, and the 54 MiB one took 77 seconds to answer.
- **SDK:** `await tools.video({path, start, end})` (`max.video(path, {start, end})` until 2026-11-14), where `path` is a file in the VM, with relative paths resolved under `/work`; `start` and `end` are numbers of seconds or strings such as `"1:30"`. Videos from the group are first copied out with `tools.file`, and Max downloads videos from the web itself (decided by the owner; yt-dlp is not installed separately). The call returns `{seconds}`, the piece's length as the guest's ffprobe has it; the host reads the copy's own length when it shows it. In the shell, it is `maxx video path --start --end`.
- **Shrunk inside the VM first** (`nix/video.js`, shared by the runner and maxx): every subsequent model call within the turn has to send the video again, so ffmpeg in the VM converts it to an MP4 at one frame per second (Gemini samples one frame per second anyway), with edges no longer than 640 and mono 32k audio, using `+faststart`. A two-minute noise test clip comes out at 3.8 MB and an ordinary one at 1.2 MB, and each conversion takes about one second. ffprobe checks the duration first, and a video over the limit is not converted. The host does not decode video: videos from the group are untrusted files and ffmpeg's parsers frequently have CVEs, so decoding stays in the VM.
- **Host** (`tools/show.rs`): reads the file under `/work` as for `tools.show`, with a cap of 32 MiB; it reads only the MP4's `ftyp` and `moov/mvhd` to obtain the duration (rounded to the nearest second, with a minimum of 1 second), and rejects anything that is not an MP4; it stores the file in the content store (and, until 2026-11-12, recorded it in the run's session). The result gains a `Part::Video { media, seconds }`, estimated at 100 tokens per second.
- **Models:** `video = true` in a model's configuration means that the model watches video; `tools::Context` carries this setting for the turn's model, and when a model that does not watch video calls `tools.video`, it receives "这个模型看不了视频" ("this model cannot watch video") (`unavailable`). On tank the setting is enabled for the Gemini models.
- **Budget:** the videos handed over in a single `run_code` total at most 10 minutes, and the same clip (same hash) counts only once; when a request is assembled, only the latest clips in tool results, totalling no more than 10 minutes, are included, and older ones are written as "[这段视频省略了，要看再 tools.video]" ("this video was omitted; call tools.video again to watch it").
- **Downgrading:** in Chat, as with images, videos go into the user message that follows the tool messages, as `[视频 n]` ("[video n]") plus a `video_url`, and the tool message says "[视频 n，见下]" ("[video n, see below]"). Responses does not accept video and writes "[这里有一段视频，这个模型看不了]" ("[there is a video here, which this model cannot watch]"); `tools.video` is not available to such models in the first place.
- **Testing:** `service/runner_tests.rs` makes a Matroska test clip locally with the dev shell's ffmpeg and goes through both the runner and the maxx paths, checking the converted MP4, the duration, the 10-minute limit per run and models that do not watch video; `max-llm` checks both downgrades; in the nested VM test, vm-check makes a clip with the VM's own ffmpeg and then runs `maxx video`, and the host reads a duration of 3 seconds.

## Web search

Decided 2026-10-29 and scheduled after the first small step of media (the owner's choice). `web_search` was implemented the same day: it is configured with `[search] api_key_file` and replies `unavailable` if that is not set; at most 4 searches run concurrently across all groups; there is no separate timeout, since the executor's 60 seconds applies; each Max tool could declare a maximum number of calls per run (`per_run`), and exceeding it replied `too_many`, but this was removed on 2026-11-05 (see the "No limits" item in [Resident programs](jobs.md#resident-programs)).

- **`web_search(query, limit?)`:** a Max tool that, on the host, calls Exa's REST API (`type: auto`, with highlights); the key stays on the host, and sops keeps using the Haskell version's `search-exa-api-key`. It returns the title, link, summary and publication date of the top results; `limit` ranges from 1 to 10 and defaults to 5; titles are capped at 200 characters and summaries at 800. Failures return `{code, message}`; the Haskell version's machinery of preferring key-free MCP, cooldowns and retries is not reproduced. A run may make at most 20 calls. Exa goes out through tank's Japanese exit, and its Chinese results are mediocre; if it proves insufficient later, Bocha or Zhipu, which are directly reachable within China, can be substituted behind the same signature.
- The tool stays permanently among the declarations in the system prompt rather than being hidden in a skill: after the Haskell version hid it in the `web` skill, the model stopped searching and answered from memory, getting plots and prices wrong (a51424d). Its guide says to search before answering what may be out of date, and since 2026-11-11 (asked by the owner) also that what the model knows ends with its training, often long before `[现在]`, so versions, releases, prices, schedules, who holds which post and recent events are searched even when it feels sure, going by the results dated nearest `[现在]`. The line for agents, its description in the list of tools, says the same in short.
- **Fetching web pages is not a host tool:** the host can reach services on the tailnet, so such a tool would open an SSRF hole. The VM image gains a `webread <url>` command: Python with trafilatura extracts the main text and converts it to Markdown, and PDFs are handled with `pdftotext` (implemented 2026-10-29; the original plan was Node's Readability plus turndown, but trafilatura avoids a set of npm packaging and also recognises legacy encodings such as GBK). It follows up to 5 redirects, with caps of 20 seconds and 10 MB, prints the first 12,000 characters and writes the full text to `/work/.max/web/`, and `--offset` continues reading from the saved full text. Tests run this script locally with the dev shell's Python against a local HTTP server. nft already prevents the VM from reaching the internal network. Pages that require JS or a login are handled with the browser (see [The browser](#the-browser)).
- Not done: answer synthesis, the model APIs' built-in search (the tools array is fixed, and programs could not obtain those results anyway), result caching, and image search.

## The browser

Not in v1. On 2026-10-29 it was first implemented as a camoufox instance started fresh for each run, and that same evening it was changed to a Chromium resident in the VM (decided by the owner); the implementation is described under "Implemented" at the end of this section.

- **Why the change:** after the model has looked at a page, the page must still be there when the next `run_code` clicks on it. The browsers that the various vendors give their models (Playwright MCP, chrome-devtools-mcp, agent-browser, Hermes's `browser_exec`) all keep the browser resident, and Hermes, like us, works in code mode: each call starts a new interpreter that connects to the same Chromium over CDP. camoufox cannot do this: as soon as a Playwright connection drops, the server closes the contexts that client opened (`cleanupContexts` in playwright-core 1.59), so keeping a page alive across processes would require writing a resident process to hold it; and Firefox no longer supports CDP. CDP state lives in the browser process, and disconnecting does not close pages; this was verified locally with Chrome and playwright-core 1.59: the pages opened, and the text typed, by one process are all still there when the next process connects.
- **Cost:** anti-fingerprinting is weaker than with camoufox. A Chromium that we start ourselves lacks Playwright's automation switches, so `navigator.webdriver` is false and HeadlessChrome is removed from the User-Agent; but the WebGL fingerprint inside the VM and the traces of CDP itself remain, so checks such as Cloudflare's block it more readily. If it does get blocked often, a resident service such as camofox-browser can be run in the VM at that point.
- There are no longer browser tools such as navigate and click; programs connect to this browser directly with Playwright. The SDK includes a snapshot helper that produces a numbered accessibility tree: the page representations that all vendors show their models have converged on this shape (Playwright MCP's `[ref=e5]`, Claude's `ref_N`, agent-browser's `@e1`), and Playwright 1.59 provides it built in, so nothing has to be written in-house. The list of "interactive elements plus CSS selectors" carried over from the Haskell version was deleted.
- Login state (decided 2026-10-29, chosen by the owner): only Max's own secondary accounts are used, stored in the profile of the group's browser, with an explicit statement that every program in the group can use them; personal logins are not supported. The Haskell version's approach, with per-person encryption and cookies hidden from programs, requires host-side tools and is left for later.
- Screenshots are handed to `tools.show` for viewing, and downloads are saved in `/work`.

Implemented (2026-10-29):

- **Service:** `max-browser.service` in the guest runs nixpkgs' Chromium with `--headless=new`, with CDP listening only on 127.0.0.1:9222; it runs as root with Chromium's own sandbox disabled, since the VM is the sandbox. The profile is in `/work/.max/chromium`, so cookies and logins survive VM restarts; profile locks left behind when the VM did not shut down cleanly are deleted before startup. It uses a Chinese UI and `Accept-Language`, the time zone Asia/Shanghai, a 1280×900 window and a memory limit of 2 GiB, and systemd restarts it after a crash (the tabs are lost, but the profile remains). It does not start at boot: the first program that needs the browser runs `systemctl start` on it, which returns only once the CDP port accepts connections. It stops along with the VM at idle shutdown, and a resident browser does not make the VM count as in use.
- **SDK:** `await max.browser()` returns the browser's single BrowserContext, and `await max.page()` returns the tab most recently opened or brought to the front with `bringToFront()`, opening one if there is none. The order is taken from Chromium's own `/json/list` (sorted by most recent activation; navigation does not count) rather than from `context.pages()`: the `pages()` that later-connecting programs receive are in the order in which Chromium attached them, not the order in which they were opened; on 2026-10-29, the very first vm-check on tank obtained, for exactly this reason, the new tab page that Chromium opens at startup, which also has a search box, and read back an empty value. After that, Playwright code is written as usual. A program connects only once. When a program ends it merely disconnects; the tabs remain for the next program to use, and programs close the tabs they have finished with themselves. `await max.snapshot(page, {selector?, depth?})` is Playwright's `ariaSnapshot({mode: "ai"})`, preceded by the title and URL: each element carries `[ref=e5]`, elements inside iframes carry refs such as `f1e2`, and `page.locator("aria-ref=e5")` finds them. `selector` captures only that element (the first match), and `depth` limits the number of levels. The refs are stored in a script that this connection injects into the page, so the next program to connect must take a snapshot first; if the page has not changed, the refs stay the same (verified locally with Chrome).
- **Packaging:** `nix/maxx.nix` (`nix/runner.nix` until 2026-11-14) bundles the runner, the SDK and playwright-core 1.59.0 (which has no dependencies and is taken directly from the npm package), and the guest's `/run/max/runner.js` links into that bundle. The former camoufox distribution, camoufox-js and its patches were deleted.
- **Fonts:** the guest has Noto Sans CJK installed, and Chromium finds it through fontconfig.
- **Tested live** (the nested test on tank, with a VM of 2 vCPUs and 1 GiB of memory): the third program of `vm-check` starts the browser, opens a data: page, takes a snapshot and saves a screenshot to `/work`; the test checks the selectors in the snapshot and the screenshot. The VM was ready in 10 seconds. The first browser start after the VM boots takes 22 seconds, mostly owing to cold reads of the store over virtiofs plus nested virtualisation; a second start in the same VM takes 4.3 seconds, and opening a page takes 0.4 seconds. With two contexts open, the run's anonymous memory was 370–410 MiB, and the cgroup peak (including page cache) was 775 MiB. Run directly on the host, loading the module takes 0.6 seconds, starting the browser 0.5 seconds and the first page 1.4 seconds. Real websites were not tested, because the test machine has no internet access. The VM's default 4 GiB of memory does not need to be increased.
- **The launch flags belong to Max** (2026-11-03; the owner pointed out that Max had no way to install extensions in the Chromium we start): `max-browser` appends the lines of `/work/.max/chromium-flags` after our own flags (one flag per line, skipping blank lines and lines beginning with `#`), and reads the file on every start. Max writes the file and then runs `systemctl restart max-browser`, which closes any open tabs. Extensions are installed with `--load-extension=<directory>`: Google Chrome stopped accepting this flag as of version 137, but nixpkgs ships Chromium, which still accepts it; `--headless=new` also runs extensions. In the nested test, vm-check writes an MV3 extension (a content script that marks the page), adds it to this file, restarts the browser, and then uses Playwright to compose a page and check that the mark is present.
- **Proposals:** the Haskell version used humanize (simulated mouse trajectories) and a virtual display (Xvfb, which is harder to detect than headless mode); here only headless mode is used for now, and these will be added if websites detect it.

opencli (added 2026-11-03, removed the same day): [opencli](https://github.com/jackwener/opencli) turns some 150 websites into commands and encodes the quirks of each site's interfaces. It was first packaged into the guest (the npm package, a lock file of our own, and a wrapper that gives each command its own tab; the nested test passed as well), but the owner reconsidered the same day: third-party tools of this kind, which offer convenience rather than primitives, are for Max to install itself when needed, rather than for us to pin to a version and keep updating; experience suggests that its adaptations to individual sites go stale quickly. The package, the wrapper and the test were removed, and the prompt keeps only one sentence: common websites have ready-made command-line tools, such as `@jackwener/opencli` on npm, and setting `OPENCLI_CDP_ENDPOINT=http://127.0.0.1:9222` makes it use the login state of the group's browser, although it will navigate one tab away. The VM can reach the internet and has Node and npm.

## GitHub

Added 2026-10-31 (requested by the owner): when someone asks Max to open a PR, Max opens it with its own GitHub account, and afterwards revises it, closes it and replies to comments itself. The account is a machine account created by the owner (GitHub requires such an account to be created by a person who is responsible for it), and it is registered with the owner's forwarding address; Max does not touch the mailbox.

Changed 2026-11-03 (decided by the owner): the two tools on the host and their rules were removed, and GitHub is reached through the host-keyed APIs (see [Host-keyed APIs](#host-keyed-apis)). Forking, cloning, pushing and opening PRs are all done by Max itself with git and the REST API, and Max judges for itself what should be done: the groups are all small, so abuse is unlikely; every model knows this workflow well; and the code for the rules outweighed what it guarded against.

- **The token stays on the host:** group members can have Max run any command in the VM, so anything placed in the VM (environment variables, `~/.config/gh`, a GitHub login in the browser) can be read out. The token is a classic token with only the `public_repo` scope: fine-grained tokens cannot open PRs against other people's repositories (not even from a fork, according to community reports; GitHub's documentation does not mention this). It cannot delete repositories (that requires `delete_repo`), nor can it access private repositories.
- **Two APIs** (tank's configuration is in nix-config):
  - `github`: `https://api.github.com`, with the header `Authorization: Bearer {secret}`, plus `Accept`, `X-GitHub-Api-Version` and `User-Agent` (GitHub rejects requests without a User-Agent).
  - `github-git`: `https://github.com`, git over HTTPS. git accepts only basic auth (tried on tank on 2026-11-03; both `Bearer` and `token` returned 401), so the secret is `base64("x-access-token:<token>")`, stored in sops as `maxx/github-git-auth`; it is the same token as `maxx/github-token`, and the two must be rotated together. Pushing uses `git push http://127.0.0.1:7777/api/github-git/<Max>/<repo>.git <branch>`; public repositories are cloned directly from github.com.
  - Neither sets `allow` or `per_hour`. `about` gives two reminders: PRs are to be opened only when group members ask for them, and the description is to end with one line in English stating that the PR was opened by an AI at a group member's request; and GitHub bans accounts that look like spam. The host does not enforce any of this.
  - The forwarder reads the entire request body, up to 64 MiB, so the pack of a single push cannot exceed that size either; response headers must arrive within 60 seconds, so a push that is too large, or that GitHub takes too long to process, is cut off. The program's `Expect` header is not forwarded: the host's own service answers it.
- **Committer:** when `[github]` is configured (currently only `login` and `user_id`), the VM's kernel command line gains `max.git=<login>,<id>+<login>@users.noreply.github.com`, which the guest writes into `/etc/gitconfig` at boot, so Max's commits are attributed to the account and the registration email address never appears.
- **Removed** (2026-10-31 to 2026-11-03): `github_push` had the guest create a bundle, after which the host created an empty bare repository, shallow-fetched the prerequisite commits, received the bundle with `fetch.fsckObjects` and then pushed, so that the host never ran git in a repository the guest had written to; `github` called the REST API and returned `{status, body}`, truncated beyond 30,000 characters. The host's rules were: writes were permitted only to Max's own repositories, the PRs and issues it had opened, and its own comments; at most 10 new PRs per 24 hours across all groups; and the host appended an AI footnote to the end of every PR description. Over three days, `github` was called 66 times (in 26 rounds) and `github_push` 9 times (in 8 rounds), without a single error.

## Host-keyed APIs

Added 2026-11-02 (requested by the owner, prompted by the wish to let Max send email): writing a tool on the host for every service that needs a key (as was done for [GitHub](#github) and [Web search](#web-search)) is too heavy. The general approach is for the host to forward HTTP requests on the VM's behalf and add the key along the way, as with the background agents' `/llm` (see [Background agents](jobs.md#background-agents)), so that the key never enters the VM.

- **Research** (2026-11-02): existing solutions fall into two kinds. One kind terminates HTTPS at the egress and replaces placeholders sent from the VM with the real key: [iron-proxy](https://github.com/ironsh/iron-proxy) (Go, Apache-2.0, rejecting every domain not listed), and Docker Sandboxes and Deno Sandbox offer the same feature. The advantage is that git, gh and SDKs need no changes; the cost is that the guest must trust a CA and traffic must detour through a proxy, while Max's VMs need to reach the whole internet (the browser, `webread`). The other kind is an explicit proxy: Fly.io's [tokenizer](https://github.com/superfly/tokenizer), which clients use as an HTTP proxy; it adds the key and sends the request out over HTTPS, with each secret bound to its permitted hosts. Since a channel from the VM to the host already exists for max's service, a proxy following tokenizer's model was written alongside `forward.rs`, rather than running an additional service.
- **Usage:** inside the VM, a program requests `http://127.0.0.1:7777/api/<name>/<path>`; the host appends the path to the configured `base_url`, inserts the key and forwards the request, and the response streams back unchanged (status code, headers, body). Both curl and fetch work; with an SDK, the base URL is set to `http://127.0.0.1:7777/api/<name>` and any value can be given as the key. No token is required: units, background commands and background agents can all call it. As with token-less `maxx`, the host cannot tell who inside the VM is calling (see [Resident programs](jobs.md#resident-programs)).
- **Configuration:**

  ```toml
  [api.resend]
  base_url = "https://api.resend.com"
  secret_file = "/run/secrets/maxx/resend-api-key"
  headers = { Authorization = "Bearer {secret}" }
  allow = ["POST /emails", "GET /emails/*"]
  per_hour = 20
  about = "发邮件，发件人写 max@example.com。文档 https://resend.com/docs/api-reference 。"
  ```

  The `about` text means "Send email, with max@example.com as the sender. Documentation: https://resend.com/docs/api-reference."
  - `{secret}` in `headers` and `query` is replaced with the key, and it must appear in at least one place. Fixed headers that carry no key (such as an API version) are also written in `headers`. For basic auth, `base64(user:password)` is stored as the secret and `Authorization = "Basic {secret}"` is written.
  - `allow` is a list of `METHOD path` entries, in which the method may be `*`; a `*` segment in the path matches any single segment, and a trailing `**` matches everything below it. If `allow` is omitted, everything is permitted. `per_hour` is a count across all groups, kept in memory and reset on restart.
  - `about`, together with the address, `allow` and `per_hour`, is placed in the system prompt, one line per API (the third parameter of `prompt::system`). If no VM is configured, it is left out.
  - Names may contain only lowercase letters, digits and `-`. These rules are checked by `check-config` when the system is built (it does not read secrets); secrets are read when max starts, and if one cannot be read, max fails to start.
- **What the host enforces:**
  - After normalisation, the path must still lie under `base_url`, on the same origin. Paths containing `%2f`, `%5c` or `%2e` are always rejected, so that the API side cannot decode them into a different path and thereby bypass `allow`.
  - The program's `Authorization` header, connection-related headers and `Accept-Encoding` are not forwarded; headers in the configuration override any of the same name.
  - Redirects are not followed; 3xx responses are returned to the program as they are. If they were followed, the header carrying the key would be sent wherever the API pointed: reqwest strips `Authorization` only when the host changes, and carries every other header along.
  - When the connection fails, the URL is removed from the error returned to the program, since the key may be in the query.
  - Every call and every refusal is logged with the group, API, method, path and status code; the body is not logged.
  - The connection times out after 10 seconds; the response headers, and each subsequent chunk, must arrive within 60 seconds.
- **What it cannot control:** the key is protected against leakage, but not against misuse. Anyone who can have Max run commands in the VM can have it call these APIs, so the mechanism suits only keys that `allow` and `per_hour` can contain, or keys the owner is willing to leave to Max's own judgement (GitHub; see [GitHub](#github)). Where a decision requires inspecting the content and control is indispensable (for example, restricting which addresses email may be sent to), a tool on the host is still the right approach.
- Code: `config::Api`, `config::Rule`, `service/forward/api.rs`; the VM service merges `/api` into each VM's routes (`vm.rs`).
