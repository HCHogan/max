# Research: the nested VM test on a Mac

Tried on 2026-11-12 and 13, as the link to tank is often unstable. The outcome: the nested test stays on bare metal (tank, or another x86_64 Linux machine); see [VMs](../design/vm.md#testing).

It runs, but too slowly to pass, so the flake has no Mac variant. The Linux builder cannot host it: the virtual EL2 that Apple provides lacks VHE, so the builder's KVM can only run in nVHE mode, the kernel rejects `kvm-arm.mode=nested`, and the test machine there has no KVM. What does work is the test driver on macOS with the aarch64-linux test machine under QEMU 11.1 or later (the deploy's pin has 10.2), which gives the machine EL2 through HVF on an M3 or later. That took three things:
  - Apple's vGIC. nixpkgs starts a test machine on macOS with `gic-version=2`; QEMU then emulates the GIC and the EL2 physical timer itself, the machine's clock jumps (from 1 s to 735 s) and it hangs in the initrd. Adding `-machine gic-version=3,virtualization=on,kernel-irqchip=on` to `virtualisation.qemu.options` (QEMU merges it into nixpkgs' `-machine`, the later key winning) uses Apple's GICv3 instead: the machine is up in about 13 seconds, with KVM.
  - Linux 6.12 in the test machine. Under Apple's EL2, KVM in 6.18 and 7.2 cannot run a VM: the VM gets no interrupts and stops early in its boot, whatever kernel it boots. KVM in 6.12 runs it. This was not bisected or reported upstream.
  - The test machine's configuration has to take its own `pkgs`: on macOS the test file's are the host's, and a darwin `postgresql` ended up in the Linux machine. nixpkgs' `qemu.forceAccel` cannot be used: its check on macOS runs `sysctl`, which is not on the build's PATH, so it never finds HVF.

  With these, the group's VM booted in 62 seconds (10 on tank), and `shell`, `run_code` over MCP, background commands and units worked; but every browser call failed, Playwright's `connectOverCDP` timing out after 30 seconds, and `vm-check` took 19 minutes. Eight cores and 8 GiB for the test machine were no faster. A benchmark one level down, a busybox guest under cloud-hypervisor, shows why: a loop that only computes runs as fast as in the test machine, and an idle guest uses about 1% of a core, but every exit (I/O, virtiofs, stage-2 faults) goes through Apple's EL2 and the test machine's KVM, so a systemd boot or a browser's start is 6 to 10 times slower. Passing would take longer time limits throughout max and the test, for one slow host. The nested test stays on bare metal, where the test machine is the only VM: tank, or another x86_64 Linux machine.
